# Agent 开发规则(通用版)

本文件是 kanzei 引擎内置的**通用开发规范单源**(编译期内嵌于 kanzei-harness)。
所有项目默认把本文件注入 agent 上下文;项目可在自己的 `.kanzei/project/conventions.md`
里**追加项目特有规则**(分支策略、架构契约、构建发版等)。通用规则一律改这里,
不要在各项目文件里复制——复制必然漂移。

## 1. 语言与沟通

- 所有回复、解释、代码修改说明、提交说明、测试说明使用项目工作语言(默认简体中文)。
- 在需求边界不清楚时,必须先提问确认,不允许在关键问题上自行假设后直接实现。
- 若问题不影响数据模型、权限、安全、外部接口、核心业务流程,可做低风险合理假设,但必须在说明中明确假设内容。
- 每次回答和修改代码前,先充分理解当前项目结构、已有实现、调用链和上下文。
- 开发时应优先复用项目中已有的函数、接口、工具方法和设计模式,不要重复造轮子。
- 涉及数据模型、权限体系、审批流程、工作流执行语义、第三方集成、部署流程等高影响改动时,必须先给出方案并等待确认,再进入实现。

## 1.1 需求取活与阻塞调度

- 需求列表按文件顺序自上而下扫描,顺序代表用户意图;priority 只用于背景判断,不得改变取活顺序。
- **`阻塞:` 字段只留给外部阻塞**——即解除权不在 agent 手里的四类:①已经把方案发给用户、正在等回复;②缺凭据/权限/环境;③依赖外部服务或他人;④用户明确宣布该条自己直营。写入时必须带**具名的解除人**(谁做什么才能解除),写不出具名解除人的就不是外部阻塞。
- **下列一律不算阻塞,不得写入 `阻塞:` 字段**:涉及多文件/跨层/数据模型(这是工作量,不是阻塞);「需先确认方案」但从未真的问过用户;上游条目自身只是被自记阻塞(伪传递阻塞);本轮没想清楚怎么做。这些只写 `进展:`,不影响调度。
- 某条一时推不动就在 `进展:` 记一句原因直接跳到下一条,不得让它拖住后续队列;`进展:` 是面包屑,不压制取活。
- blocked 项不得被误标为 done;解除阻塞后再恢复推进。追踪工具没有 blocked 状态时保留原状态,调度器以 `阻塞:` 字段判断跳过。
- 触碰任一条目时顺手复核它的 `阻塞:` 是否仍成立:解除条件已满足、依赖已归档、方案早已确认的,**当场清空该字段**。阻塞只进不出会在若干轮后锁死整个队列。
- WIP 上限只数**可执行**活动项:需求与缺陷合计只允许 1 个可执行活动项(requirements 的 doing 与 defects 的 fixing 合并计数,共用同一个槽位)。带合法「阻塞:」字段(或用户明确挂起)的 doing **不计入准入配额**——阻塞项自动让位,不得以「doing 名额已满」为由拒开新条目。防堆积兜底:含阻塞在内 doing 总数 >4 时不得再开新项,必须先收敛存量。
- 已完成的 doing 需求必须立即用 `req update <id> done` 关闭。
- **全部条目都 blocked 是队列异常,不是可接受的终态**。此时必须:先逐条复核并清掉不成立的阻塞;复核后仍全阻塞,才回复用户并**逐条点名缺的是哪一个具体决策**。禁止以「没有可执行条目」「本轮停止」之类的纯文本收尾。

## 1.2 关闭边界:可用即关闭

- 缺陷/需求以「功能可用」为关闭界:核心行为已实现、有可运行的自动化验证(单测或集成任一)即关闭;不因缺 E2 夹具、UI harness、并发压测等验证增强项长期滞留 fixing/doing。
- 残余验证与质量缺口不丢弃:关闭时转移到专门条目或新开需求/缺陷,并在关闭条目进展里注明去处。
- 不允许关闭的情形:验收的功能性条款未实现、存在已知数据丢失或安全风险、或没有任何自动化验证。
- 判定口径:问「现在用它会不会坏」,而不是「测试矩阵是否完备」。

## 1.25 完成判定与验收证据

- 关闭需求或缺陷前必须逐条对照验收原文,每个验收项都给出精确代码位置或其他可复核证据;不得用笼统的「已实现」「测试通过」代替逐项说明。
- 声称完成的能力必须存在真实调用方或消费者;没有消费者的命令、死代码、只展示但未接入真实数据源的界面壳均不算完成。
- 沿用既有实现时必须显式标注哪些是既有能力、哪些是本次交付,不得把既有能力重新申报为本次产出。
- 验收原文中的平台、端、环境、用户范围及其他范围限定词不得在结项时缩小;实现只覆盖其中一部分时必须保持活动态并写清缺口。
- 任一验收项缺少实现、调用方或可复核证据时,不得进入 `done`/`fixed`;应保持 `doing`/`fixing`,直到缺口补齐。

## 1.35 标签与依赖字段

- 标签受控词表(单选):前端 | 后端 | 核心 | 模型 | 发布 | 流程。
  前端=界面与交互;后端=服务命令/会话/存储/tracker;核心=runner/harness/tools/memory/CLI 引擎;模型=provider 协议/凭证/限流;发布=构建/安装/更新;流程=规范/度量/验收/测试基建。
- `依赖:` 只列**仍未完成**的阻塞项;依赖关闭后在下次触碰该条目时把它移入 refs——已满足依赖滞留在依赖字段会让取活调度误判阻塞。

## 1.3 工作粒度与验证选择

- 单轮粒度 = 一个完整条目:以做完当前这一条缺陷/需求为目标;同构批量改动一轮吃掉完整类别,禁止两三处一轮的微切片。
- 确实超出单轮容量才按验收子项分轮,并在进展里写明批次边界。批数由 agent 按条目实际工作量自定,**上限 10 批**,并写入 `批次: k/N`;超过 10 批说明条目太大,应收口关闭并把剩余开成后续条目。
- 验证与改动面匹配:纯前端(html/js/css)改动跑语法检查与运行时冒烟即可;动了后端代码跑**定向测试**(如 `cargo test -p <改动 crate>`);与改动无关的套件不跑——无信息量的测试本身就是浪费。**全量测试不再挂在每次提交上**,触发点与频率见 §1.4。
- **前端改动不得只以语法检查作为验证证据**:它只查语法,查不出运行时错误、初始化崩坏和渲染错位。必须同时跑运行时冒烟,且新增的交互要在冒烟里留下对应断言——修了什么就断言什么,否则同类回归下次照样溜过去。

## 1.4 验证与提交节奏参数

- **定向测试**:每次提交前必跑——改动哪个模块跑哪个模块的测试;改动被广泛依赖的模块时,另加依赖方编译检查;纯前端改动 = 语法检查 + 冒烟(秒级,不降频)。
- **提交前代码门禁(D-264)**:提交 Rust 源码前,`compile_gate` / `fmt_gate` / `clippy_gate`(kanzei-tools/src/git.rs)会由结构化 git 工具**代码强制**跑一遍 `cargo check --workspace --all-targets`、`cargo fmt --all -- --check`、`cargo clippy --workspace --all-targets -- -D warnings`,任一不过即拦下提交并点名违规文件。这条规则在 2026-08-11/12 被自举漏掉三次才确认必须强制,不要再尝试用 bash 绕开;CI 与 verify.ps1 与门禁命令逐项对齐,改动任一处必须同步另两处(守护测试 `stage_fmt_clippy_gates_align_with_ci_and_verify`)。
- **全量测试**:默认只有两个触发点——①**复杂度中/大**的条目关闭前一次(复杂度小的条目关闭**不跑**全量,定向测试照常;未评估复杂度的先补字段再判定,不默认免测);②发版前。
- **提交频率**:默认一条目一提交;多批次大条目(拆解/迁移类)每批一提交作为回滚锚点——提交本身不再附带全量成本。
- **push 频率**:条目完成后 push;多批次条目建议每批提交后顺手 push,让 CI 对每次 push 异步跑全量兜底——CI 红了先修再开下一批,不阻塞本地节奏。
- 不可调降的底线:发版门禁全量与 CI 独立全量;任何全量红灯(本地或 CI)当场修复,不得带红推进。

## 2. 代码修改原则

- 不要引入不必要的框架、抽象层、兜底逻辑或兼容逻辑。
- 不要为了「看起来完整」而实现简化版、替代版或占坑版功能。
- 如果某部分暂时无法完整实现,可以明确留下 `TODO`,但不能用低质量简化实现代替正式实现。
- 任何有风险的实现,必须先说明风险点,再进行修改。
- 不允许在需求不清楚、数据结构不确定、接口行为不明确的情况下自行扩展实现。
- 修改应保持小步、可验证、可回滚,避免把无关重构和业务改动混在一起。
- 不要改动与当前任务无关的文件,不要混入无关格式化。

## 3. 命名与代码风格

- 项目内部统一使用 `snake_case`。
- 字段名、变量名、函数参数、请求参数、返回数据结构在业务代码中都应统一为 `snake_case`。
- 如果第三方接口返回 `camelCase`,必须在调用层或适配层统一转换为 `snake_case`。
- 业务代码中不应额外兼容或兜底读取 `camelCase` 字段。
- 禁止在同一模块或同一数据流中混用 `snake_case` 和 `camelCase`。
- 前端如果受框架限制必须使用组件事件或库约定命名,应限制在 UI 层,不得污染后端 API 契约和业务数据结构。

## 5. 终端与命令规则

- 默认终端环境按项目约定(默认 PowerShell);除非明确是在外部 Linux 服务器上执行,否则不要使用 Linux 风格命令。
- 本地命令应优先使用与默认环境兼容的写法,避免使用会报错的命令。
- 如果要进行长时间训练、部署、批量迁移、长时间构建等流程,先给出指令让用户来执行。
- 执行命令前应确认当前目录。
- 运行测试、构建、格式化前,应说明将验证什么。
- 不要执行破坏性命令,除非用户明确要求并确认风险。

## 6. 分支与提交流程(通用纪律)

- 开发前 `git status` 检查工作树,提交前确认只包含本次任务的必要改动。
- 提交只暂存自己明确修改的文件;禁止 `git add .` 或目录级扫入,避免把并发/无关改动卷进提交。
- commit message 使用中文或英文均可,但一律**不带任何 Co-Authored-By 署名**。
- 提交前确认工作树干净且本次改动全部归属明确;提交后核对实际提交的文件与预期一致,不一致立即补正。
- 分支策略(默认分支、合并流程、发布树)由项目特有规则定义。

## 7. 测试与验收

- 代码修改完成后,必须提供测试用例。
- 测试说明需要包括:测试什么功能;如何触发测试;预期结果是什么;什么情况下算测试完成。
- 修改后应优先运行与改动相关的最小测试集。
- 对于核心流程、权限、审批、工作流、数据库迁移、前后端契约变更,需要补充重点回归测试范围。
- 前端改动至少需要说明:影响页面;用户操作路径;预期 UI 状态;失败或空状态表现。
- 后端改动至少需要说明:影响接口;请求和响应字段;权限要求;错误码或异常行为。
- 部署完成后,需要根据测试用例验证功能是否正确。

## 8. 文档与计划维护

- 每次完成大规模改动后,及时更新相关的 plan、设计说明或项目文档。
- 必须维护的文档有需求文档和缺陷文档;维护归档的和现在进行的每次长上下文修复后记得更新,并且在最近的一次对话引用。
- 小修 bug 不强制更新设计文档,但最终说明中必须写清影响范围。
- 文档更新应反映真实实现,不要写尚未完成的功能为已完成。
- 如果存在未完成事项,应明确标记为 `TODO` 或后续计划。
- 文档中的产品状态、技术状态和 TODO 必须保持一致,避免同一能力同时被描述为「已完成」和「未完成」。

## 10. 任务级并行

- 每条可写开发线必须绑定独立 git worktree 与独立分支;同一代码树最多绑定一条线。同一棵树上的多个 writer 仍要排队,不能把覆盖文件叫作并行。
- 代码写入只落本线 worktree。交付通过逐线 diff、merge-tree 预检、`--no-ff` 合并与冲突处理进入主线;禁止用项目级 run 租约把不同 worktree 的整轮执行重新串行化。
- 项目文档、状态库与项目记忆只认主根一份。线内 `cwd` 是 worktree,`project_root` 是主根;从 worktree 运行时必须显式传项目根参数。
- 多线协作不是独占执行。每条线开跑与刷新时都要看到其他活跃线的认领、分支与改动文件;提交只暂存自己明确修改的文件,提交前重查协作状态、工作树和 staged diff,禁止 `git add .` 或目录级扫入。
- 合并前显示各线真实运行态与文件集合交集;文件交集和 git 预检只覆盖**文本层**。语义撞车不会被 git 保证检出,界面必须常驻「文本层已检查 · 语义层未检查」,不得把空冲突表述成语义安全。
