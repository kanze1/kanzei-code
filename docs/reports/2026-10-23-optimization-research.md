Kanzei 下一阶段优化调研 · 2026-10-23
=================================

建议把下一阶段的目标定为：**利用项目知识，稳定地接续并交付真实任务，同时减少用户重复解释、人工核对和等待。** 执行顺序是先收口当前交付基线，再验证项目记忆的增量收益，随后按测量结果优化上下文与耗时，最后扩展浏览器任务覆盖。

本次只读检查了当前源码、活动 tracker、近期报告和已有验证回执，并查阅第一方产品文档、工程文章与原始论文；新增本文，没有运行模型实验、完整测试、发布或修改实现。以下“已有实现”与“本次实测通过”严格区分。优先级和实施范围是本次分析建议。

本文保留调研时点的证据与建议，不作为持续更新的任务队列。随后按用户授权完成的文档纠正见 [文档维护记录](2026-10-23-documentation-maintenance.md)；当前导航见 [文档入口](../README.md)，活动范围仍以 tracker 为准。

**二、按投入顺序排列的四个方向**

| 顺序 | 方向 | 用户实际得到什么 | 复用基础 | 第一批范围 |
| --- | --- | --- | --- | --- |
| 1 | 任务交付、恢复与真实验收收口 | 清楚知道完成了什么、证据属于哪个版本；中断后可靠接着做 | deliver 账本、task/run 事实、验证注册表、原生 UIA harness | 一条任务从执行、停止/恢复、验证到提交和重启回读的完整路径 |
| 2 | 项目记忆带来的快速复工 | 重新进入项目时少解释、少重复调查、少再犯同类错误 | ProjectKnowledge、memory lifecycle、来源快照、回放评估 | 固定任务对照 + 依据结果修复召回/知识组织中的实际失效点 |
| 3 | 成功任务的时间与成本 | 更快获得可用结果，长任务少重复读取和压缩 | 用量事件、task metrics、tool_search、工具产物引用 | 逐步成本与阶段耗时归因，然后只改最重的开销来源 |
| 4 | 浏览器与研究的完整任务 | 能持续完成表单、调试和有来源的研究交付 | 已有连接/页面身份、语义动作、webfetch/source 存证 | 三类固定真实流程，覆盖导航、恢复与结果核对 |

方向 2 是长期差异化价值最高的投入；方向 1 是让这些改进可靠进入日常使用的近期前提。方向 3 与方向 2 共用评价集和观测数据，不需要另建一套平台。

**方向 1：把已实现能力交付为可信的完整任务**

当前最直接的信号是源码、tracker 叙述、验证回执与提交基线之间存在时间差。D-765 仍为 open，描述代码提交与 tracker 关闭记录分离；R-101 仍保留原生桌面路径验收。与此同时，R-353 所需的部分账本消费已经在源码中。下一步应先逐项核对剩余验收，再修复具体断点。

建议复用现有事实源，让对话中的完成结果与管理页显示同一组事实：改动所属条目、提交、验证覆盖、产物位置及剩余动作。模型的完成声明不自动替代环境中的结果。大改动按关切形成可审阅提交，避免把当前所有改动合成一个不可归因的发布。

最小验收流程：创建任务 → 产生变更 → 用户插话或停止 → 恢复 → 检查结果 → 记录交付 → 重启应用 → 回读同一结果。加入等待批准、测试失败、提交未完成、后台任务迟到回报等变体，确认不同阶段不会被显示为同一种“完成”。沿用已有状态与事件，不再增加平行状态机。

外部依据：Anthropic 的长期任务实践指出，压缩不能单独解决跨会话工作，明确进度工件与端到端验证很关键；其 agent eval 指南进一步区分模型轨迹与环境最终结果。这里借鉴的是行为与评价合同。[长期任务 harness](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)、[Agent 评估方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

回退体验可以参考 Claude Code 对代码、对话和定向摘要分别处理的合同；该产品也明确限定了文件检查点的覆盖范围。Kanzei 应基于自身已有检查点与事件能力描述可恢复内容，避免把会话回退与外部副作用撤销混为一谈。[Checkpointing](https://code.claude.com/docs/en/checkpointing)。

完成判据：当前批次拥有绑定最终干净提交的本地完整验证，并有同版原生用户路径证据；tracker 进展、交付账本和界面结果可以互相核对。完整门禁通过不自动覆盖所有真实设备场景。继续遵循仓库规则，不启用 GitHub Actions CI。

**方向 2：让项目知识真正缩短下一次任务，而不止保存更多内容**

这是 Kanzei 最值得长期投入的方向。当前代码已具备层级区域、依赖关系、相关记忆、来源和生命周期；缺少可直接用于本轮决策的，是新版本在真实任务上的稳定收益证据。

重新读取的 10 月 6 日冻结实验给出了很好的起点：8 类问题、每臂各重复 2 次，共 16 对有效比较；完整答对均为 16/16。工具调用从 30.25 降到 27.31（-9.71%），累计输入减少 8.65%，但平均探索耗时从 105.4 秒到 106.2 秒（+0.76%），未缓存输入仅减少 0.46%。记忆召回路径题平均更慢 58.8%。该报告的 bootstrap 区间包含零。这是旧版本、小范围实验，不能代表当前实现；它说明应优先追查“知识为什么没有稳定省时间”。[冻结实验报告](../../dist/exploration-ab-20261006/report.md)。

建议先从已有知识投影输出一份紧凑的任务相关上下文：涉及模块及上下游、有效约束、已知踩坑、证据出处、验证入口、未完成事项。已有字段与来源足够时直接复用；只有遇到可复现的缺失再扩展数据合同。大段证据保留可回读引用，模型需要时展开。

评价集应覆盖：新模块定位、隔天继续任务、跨模块修改、旧结论被新代码推翻、用户纠正后的下一次任务、压缩后的恢复、同一项目不同工作树。采用反馈只证明明确采用，不自动证明最终结果改善；同样，未命中也不自动证明无用。

外部依据：2026 年 5 月的 LongMemEval-V2 将环境经验分成静态状态、动态变化、工作流程、踩坑和前提判断，适合借来设计项目生产力问题。论文自标 Work in Progress；它的网页环境问答成绩不能外推为 Kanzei 编码收益。[原始论文](https://arxiv.org/abs/2605.12493)。Anthropic 的上下文实践支持轻量引用、按需展开，也明确指出运行时探索可能增加延迟，因而应按任务验证混合策略。[Context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)。

建议首批预先固定 12 个代表性任务，每个任务在相同源码、模型、权限、输入和初始记忆条件下比较当前策略与一个候选改动，每臂至少重复两次。这个规模用于筛查方向，不用于宣称统计稳定或估计可靠的 P95。保留失败、退化和基础设施异常，预先写清补跑规则。低成本回放用于定位行为；真正的修改任务仍要执行结果校验。当前 `kz replay-eval` 回放录制工具结果，不实际执行外部工具，不能单独证明完整任务完成率。[现有回放合同](../../crates/kanzei-core/src/replay.rs)。

主要判据：任务成功与事实正确性、恢复到有效工作所需时间、人工纠正次数、过期知识误用、重复读取量和实际模型用量。收益不成立就调整召回与组织策略，再跑同一批任务；不以增加记忆数或召回次数作为完成条件。

**方向 3：围绕成功任务优化延迟、上下文和缓存成本**

当前已有 `tool_search` 与 resident/deferred 分层，供应商适配和桌面 StepEnd 也已有 cache read/write 信息。与此同时，持久化 `EpisodeRecord`、`TaskRoundProjection` 与 `TaskTrend` 的显式字段主要是输入/输出总量和时长；活动 R-373 仍要求逐步缓存测量。应把“协议拿到了用量”与“能够跨重启比较每个任务的缓存成本”区分开。

建议先补齐一条可核验的归因链：模型等待、工具执行、权限等待、排队、验证、压缩与记忆维护各占多少；每步的未缓存输入、缓存读取/写入、输出与工具结果体积如何累积。复用事件与运行画像，避免创建第二套统计来源。费用按供应商、模型和适用计价分别计算；拿不到价格或计费口径时展示 token 分项，不虚构成本。

根据结果再选择优化：减少重复读取相同内容；对子代理结果保留结论与证据引用、必要时局部复核；大工具输出按需读取；维持稳定请求前缀；对独立读取批量调度。不能只减少输出字符却让模型增加搜索轮次，也不能为了缓存而保留已经无效的约束。

外部依据：Anthropic 的工具搜索与程序化工具调用把发现工具、处理大量中间结果与模型推理分开。其缓存与节约数字来自自身协议和测试，应作为候选机制依据，不能作为 Kanzei 的预期收益。[Advanced tool use](https://www.anthropic.com/research/advanced-tool-use)。

完成判据：在方向 2 的固定任务集上，成功率与结果质量不退化，成功任务耗时和实际用量呈现可重复改善；同时呈现失败任务消耗，避免只统计成功样本。较大的样本积累后再比较 P95、压缩频率和极端慢任务。

源码入口：[事件用量](../../crates/kanzei-app/src/run/events/mod.rs)、[任务画像](../../crates/kanzei-core/src/store/task.rs)、[轮次记录](../../crates/kanzei-core/src/store/mod.rs)、[工具目录](../../crates/kanzei-core/src/runner/drive/tool_catalog.rs)。

**方向 4：把浏览器与研究能力打磨成可重复完成的用户流程**

当前浏览器合同已经要求连接动作携带 `connection_id + page_id + expected_url`，iframe 也有独立身份；已提供表单语义动作和按 topic/task 绑定的正文存证。`webfetch` 已保留原文、最终 URL、时间、内容工件及 hash。10 月 18 日报告还保留了四对象检索、缺失来源披露和一张原生表单的历史实测。这些都应纳入现有能力，而不是继续沿用旧清单中的“缺接线”。

下一批只选三类任务：已有登录会话中的表单填写与错误修正；本地应用的浏览器调试与回归确认；跨多个来源的研究回答与出处回读。对每类分别验证页面跳转、标签页变化、iframe、断开连接、取消和恢复。成功由目标应用回执、状态变化或可回读正文核对。

产品上优先降低使用成本：用户能看清连接的是哪个浏览器/页面、当前动作及最终结果；研究输出能从结论跳回对应版本的原文。是否扩展浏览器持久化或更多原生应用，应由这三类流程的实际失败记录决定。

外部依据：Cursor 的浏览器文档将页面操作、截图、控制台和网络观测纳入开发流程，并说明按工作区保留浏览器状态；值得借鉴的是任务连续性和可调试性，不是照抄其整体产品形态。[Cursor Browser](https://cursor.com/docs/agent/tools/browser)。

完成判据：各流程在稳定身份和明确结果检查下重复完成；控制动作成功、页面显示成功、业务结果真正成立分别记录。已有页面 hash 是来源完整性的基础，引用是否支持结论仍需内容评价。

**三、建议的首个实施包与停止条件**

1. 对当前工作区按关切核对实现、tracker 和已有回执，先处理 D-765 对应的提交与关闭记录一致性；已有 ledger 消费和记忆/浏览器能力以剩余验收为范围。
2. 形成可审阅的提交后，运行本地 `scripts/verify.ps1` 的相关检查，最终干净提交再运行 `scripts/verify.ps1 -Full`；选择原生的执行、停止、恢复、交付回读流程验证同一构建。
3. 固定首批项目任务与对照条件，先测现状，再仅改变一个知识或上下文策略。评价工具复用已有 trace、replay、metrics 和验证注册表。
4. 只有在真实任务暴露出收益瓶颈时，扩展召回策略、缓存请求适配或浏览器操作。若瓶颈来自测试/工具等待，就优化对应执行路径；若来自错误的项目知识，就修知识的范围、时效与检索。

此阶段暂缓：仅按文件行数进行全库拆分、再造一套记忆存储、扩大代理数量、泛化的全桌面自动化和更多工作台入口。它们只有在上述真实任务出现明确瓶颈时才进入下一批。现有大型函数可以在相关合同被修改时按职责整理。

建议每批交付都回答同一组问题：用户少解释了什么、少等待了多久、少做了哪些人工核对，以及新版本是否在相同任务中保持正确。这样优化方向会由可复现的使用收益决定。
