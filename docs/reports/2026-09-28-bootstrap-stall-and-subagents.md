## 2. 自动校验器把检查环境问题反馈成了代码错误

161 次写文件中，131 次返回“局部结构校验发现……精确错误，请先修复后再扩大回归”。并非所有失败都是假错，其中也有真实语法错误、格式差异和编译诊断；但以下检查配置错误已确认：

| 问题 | 运行证据 | 源码与最小复现 |
| --- | --- | --- |
| Rust edition 未传入 rustfmt | 53 次首错为 async fn 不允许用于 Rust 2015；另 3 次为 async move 要求 Rust 2018+ | `Cargo.toml:16` 使用 2021；`crates/kanzei-tools/src/local_validation.rs:220` 调用 `rustfmt --check <file>`。合法 async 最小文件不带 edition 时退出 1，带 `--edition 2021` 时退出 0 |
| VM 冒烟命令漏启动参数 | 19 次 vm_runtime_probe 失败，包含 SourceTextModule 不是构造器 | `local_validation.rs:210` 用 `node scripts/ui-runtime-smoke.mjs`。本机 `typeof require('node:vm').SourceTextModule` 默认是 undefined，加 `--experimental-vm-modules` 后为 function |
| 小改动后运行整套 UI 检查，却统一限制 20 秒 | 18 次首错为命令超过 20 秒 | `local_validation.rs:17` 设定 20 秒；`scripts/ui-lint-smoke.mjs:136` 起继续调用界面图库、列布局、窄屏、星图浏览器检查，并非单文件快速检查 |

上述计数是诊断出现次数，不能相加当成独立写入次数。写入本身成功、工具通常仍返回 is_error=false，但诊断要求模型先修错误，增加了反复排查与上下文噪声。现有记录不足以把全部 110 分钟精确分摊到某一个原因。

应当修正命令参数，并区分“代码失败 / 检查环境失败 / 超时未完成”。单文件写入后只执行便宜的相关检查；跨模块和浏览器回归在批次边界合并运行，避免每个补丁都重新启动整套验收。

## 3. 无限单次执行没有批次交付边界

真实事件中，331 次 session.turn_started 的 max_steps 全部为 0。该值表示主代理不受步数上限截断。`crates/kanzei-app/src/run/events/mod.rs:612` 的临近预算收尾逻辑遇到 0 直接退出，因此有限预算下的收尾提示不会生效。

`crates/kanzei-core/src/runner/drive.rs:542` 的周期提示只要求说明已完成/剩余工作，并明确要求继续。它没有要求结束当前批次、提交或保存可恢复的交付检查点。截图中反复出现的 B3/B4 已完成、B2a 仍在接线，与这一行为一致。

`crates/kanzei-app/src/run/coordinator.rs:397` 在 run 返回后才评估下一轮自动推进。`crates/kanzei-harness/src/auto_run.rs:383` 的无动作保护也在轮次边界执行。工作树持续变化又会改变进展签名（`crates/kanzei-app/src/auto_run.rs:214`），不能据此证明形成了可交付进度。

这解释了截图中的“内部 331 步，但自主推进 0 轮”：内部运行尚未正常交回外层调度，随后被用户停止。长期自主运行需要保留，但每个实现批次必须有独立收口，不应等待模型自行结束整条大需求。

建议的正常流：领取一个有限批次 → 实现 → 定向验证 → 隔离当前批次改动并提交 → 回写进展与下一步 → 生成上下文摘要 → 自动继续下一批。不具备提交条件时保存补丁、真实失败与下一步检查点；不能为了计数强制提交混杂工作或把失败标为完成。步数/时间阈值用于触发收口，不直接把控制权交还用户。

## 4. 压缩连续两次失败后失去主动恢复

最近运行记录两次 `compaction refused: tool call/result pair crosses the compaction boundary`，无成功 context.compacted 事件。

`crates/kanzei-core/src/runner/compaction.rs:130` 先按 token 估计选择切点，152 行发现切断工具调用/结果配对便直接返回 0，没有向邻近合法边界移动。`runner/drive/context_budget.rs:127` 将零收益计入 futile；`runner/mod.rs:130` 上限为 2。连续两次后，当前 run 的主动压缩路径不再尝试，后续只能依赖其他裁剪或被动恢复。

应保留配对完整性检查，同时选取合法消息边界，并区分“摘要无收益”和“切点无效”。已有新条目清理只在换条目时触发，同一 R-365 长期运行不能靠它解决。

## 5. 并行线路与子代理需要统一状态、区分职责

最近一轮调用 collaboration_status 21 次，全部返回 “No other line is currently running in this project.”。这些工具自身累计执行仅 233 毫秒，不能把它们直接说成耗时主因，但它们重复占用模型决策步骤和上下文，而且查询对象不符合当前委派方式。

`crates/kanzei-app/src/collaboration.rs:143` 收集同项目其他 AppState 线路，并排除当前线；它没有查询 task 的子代理运行注册表。408 行上下文提示和 474 行工具描述又要求编辑共享文件/暂存前调用，因此空结果也反复出现。

本轮确实有两个 task 在 05:02:09 同时开始，分别跟踪托管事件消费和协议回放路径，约 36 秒/34 秒完成。因此系统已有真实的并行子代理。不过 `crates/kanzei-tools/src/profiles/dev_system.md:15` 与 `crates/kanzei-core/src/runner/subagent.rs:218` 仍限定普通 task 为只读勘察，主代理承担修改与提交。R-369（后台、可写 worktree、自定义 agent、续聊）当前仍为 todo、0/3。

建议沿 R-369 改造，不再创建第二套委派系统：

| 对象 | 职责与边界 |
| --- | --- |
| 主代理 | 选择批次、分派明确工作、整合修改、验证并提交；统一回写项目进展 |
| 子代理任务 | 勘察、隔离实现、验证；展示父任务、task_id、状态、作用目录、结果与证据；实现任务使用自己的 worktree |
| 其他用户会话/线路 | 保留独立会话身份；其并发写入风险仍需可见，不能因子代理面板为空就忽略 |
| 引擎 | 维护统一活动快照；状态改变时通知主代理；在派发、整合、暂存等边界刷新冲突判断，而不是要求模型反复手动查询空列表 |

界面显示清楚“谁在做什么、产物到哪一步”，不能把同级会话数量直接当作子代理数量。单项目保持轻量，不另起常驻调度模型。

## 6. 修复顺序与验收

1. 修自动校验：正确传递 Rust edition / VM 参数；快速检查与批次回归分离；超时或环境缺失不会伪装成代码错误。最小合法文件通过，真实语法错误仍可识别。
2. 修合法压缩边界：连续工具调用、并行结果、重放消息下均保留完整配对；无效切点可恢复，不耗尽无收益预算。
3. 增加批次收口：有限批次可自动验证、隔离提交、记录进展后继续；长任务不能只靠反复文件编辑维持“有进展”。与 R-358 的工作单元/批次口径衔接，保持机器验收与用户体验验收分离。
4. 衔接 R-369：统一线路与子代理状态，可写任务隔离、完成通知和结果整合；验证运行中的两个 child task 可见，独立用户线路仍可见，空闲时不重复注入空查询。
5. 用 Markdown 手机阅读器跑一个真实、范围明确的开发批次，再加第二项目验证并行。记录批次用时、有效验证次数、诊断噪声、提交次数与任务归属；不以工具调用总数代表完成度。
