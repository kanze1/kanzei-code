# 设计与 AI 讨论记录规范

本目录记录已经形成方案、仍在演进中的设计讨论，以及与需求、缺陷和技术决策之间的证据链。它不是聊天全文的存档，而是团队可检索、可复用、可回溯的设计知识资产。

## 记录分工

| 记录 | 真源 | 适合记录 |
| --- | --- | --- |
| 需求/缺陷 | `.kanzei/project/requirements.md`、`defects.md` | 要解决的问题、验收条款、当前状态和阻塞 |
| 设计文档 | `docs/design/*.md` | 背景、讨论摘要、候选方案、方案演进、实现边界和验证证据 |
| 技术/产品决策 | `.kanzei/project/decisions.md` | 已经需要长期复用的稳定约束、取舍和重议方式 |
| 架构索引 | `.kanzei/project/architecture/README.md` | 已验证架构事实与设计入口 |
| 开发规范 | `.kanzei/project/conventions.md` | 所有轮次都必须遵守的工作和验收规则 |

原始 AI 聊天不作为规范真源。讨论结束或方案发生重要变化时，提炼摘要、参与者/来源、结论和证据；需要保留原文时，应放在明确的外部来源或运行轨迹中，并在设计文档中记录引用。

## 设计文档最小结构

新的设计主题使用一个 `snake_case` 文件名，并至少包含以下内容：

```markdown
# 主题

- 状态：草案 | 设计基线 | 已验证 | 已废弃
- 日期：YYYY-MM-DD
- 关联需求：R-xxx
- 关联缺陷：D-xxx
- 关联决策：A-xxx

## 背景与问题
## 目标与非目标
## 讨论摘要
## 候选方案
## 最终方案
## 技术选型与取舍
## 实施边界与调用方
## 变更记录
## 验证证据
## TODO 与后续风险
```

没有适用的需求、缺陷或决策时明确写“无”，不得用无关 ID 凑引用。文档只把已实现或已验证的事实写成结论；未完成内容使用 `TODO`，并与追踪条目状态保持一致。

## 决策与方案变更

- 设计文档中的最终方案引用对应的 `A-*` 条目；`A-*` 条目反向引用设计文档。
- 只有稳定的长期约束才进入 `decisions.md`，讨论中的方案保持 `draft`，用户接受后再转为 `accepted`。
- 方案变化不得覆盖旧结论：新建决策记录原因、影响和迁移/回滚边界，并将旧决策转为 `superseded`；明确否决的方案转为 `rejected`。
- 每次更新设计文档都在“变更记录”追加日期、变化、原因和关联 ID。
- 技术选型至少说明候选方案、选择理由、主要取舍、影响范围和验证方式；涉及数据模型、权限、外部接口或发布流程时，另附迁移/回滚或边界说明。
