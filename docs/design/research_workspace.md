# research 工作台前端设计(R-276 批1 设计稿)

- 状态: **待用户过审**(2026-08-16 首轮 research 实测后,由用户逐条反馈驱动)
- 实施条目: R-276(前端)、D-413(交互接线缺陷)、R-277(引擎,计划树/引用校验)
- 设计输入: [research_mode_prior_art.md](research_mode_prior_art.md) §1 前端横评(Gemini/ChatGPT/Perplexity/Manus 四家)、[research_mode.md](research_mode.md) §3 工件契约、2026-08-16 首轮真实研究会话的实测反馈
- 一句话: 研究模式现在是「dev 界面 + 侧栏挂两个列表」,要变成**独立的研究工作台**——报告是主角、来源可溯可开、条目可改可删。

## 0. 问题诊断(全部有证据)

用户首轮实测后的六条反馈,逐条对到代码:

| # | 用户反馈 | 代码事实 |
| --- | --- | --- |
| 1 | research 和 dev 有点混 | research 档只在侧栏多一个 section(index.html:98-107),主区仍是 dev 的需求/缺陷/目标/测试/git 全套;模式标识只有状态栏一行小字 |
| 2 | 前端做得不好 | 研究工件是二等公民:两个扁平列表 + 一个 report ↗ 按钮,无详情、无筛选、无反查 |
| 3 | 摘要够广度,但要能读正文 | `read` 不支持 PDF(read.rs 无 pdf 处理);arXiv API 只返回 summary;正文通道缺失 |
| 4 | 文本呈现不方便、交互不舒服 | 标题被截断成「kanzei 检索/触发/反事实评估实现(index...」;confirmed 条目整条置灰像被禁用 |
| 5 | 想直接打开参考文献也不行 | `.kanzei/research/sources.md` 每条文献都有 `- URL: https://arxiv.org/abs/...`,UI 不渲染为链接 |
| 6 | 删不掉,打开也不能编辑 | renderDocList 把交互 gate 在 `kind==="req"||"defect"`(11-docs-list.js:249-262);后端 docs_update 对 source/finding 全支持(docs.rs:402-413)——**纯前端接线缺失**(D-413) |

**共性根因**:数据层其实很规整(来源有 URL/作者/年份/类型/要点,发现有 域/等级/结论/证据锚/refs),**前端把结构化数据渲染成了截断字符串**,并且没接后端早已具备的写通道。这与 2026-08-16 波次审计抓到的「最后一公里不接线」是同一个失败模式。

## 1. 设计原则(取自先行对照)

1. **结果 > 过程**:报告是主角,研究步骤折叠在报告下方(Gemini 式层级最明确;Manus 式过程占屏是反例)。
2. **溯源冗余**:内联引用 + 来源卡 + 独立来源页,三处都能到达同一来源(Perplexity 式;溯源是研究的命根,冗余不是浪费)。
3. **计划先行、可编辑、运行中可转向**(Gemini/ChatGPT;引擎侧由 R-277 提供数据,前端先留位)。
4. **四组件 schema**:document(报告)/ steps(活动)/ sources(来源)/ annotations(内联引用)——各家差异只在权重分配。
5. **数据已结构化的,UI 不许降级成字符串**:有 URL 就必须可点,有 file:line 就必须可跳。

## 2. 模式分离(反馈①)

- **research 档**:主区默认进「研究工作台」视图;activitybar 收起 dev 专属入口(需求/缺陷/目标/测试/git),避免研究时对着 backlog 发呆。
- **dev 档**:研究入口完全不出现(现状已如此,保持)。
- **模式标识升级**:从状态栏一行小字提升为 activitybar 顶部的模式徽章(research 用区别色),一眼可辨、点击可切。
- **共用不变**:对话、文件、设置、记忆四处两档共用,不做分叉。

## 3. 工作台布局(反馈②④)

左会话 / 右研究面板(Gemini 式双面板),右面板三段 tab:

### 3.1 报告 tab(默认)
- `report.md` 渲染复用既有 markdown 管线(04-markdown.js)。
- **内联引用**:`[S-00x]` 渲染为角标链接,点击滑出该来源卡;`file:line` 渲染为链接,点击打开文件并定位行。
- **V 等级徽章**:V0 灰 / V1 蓝 / V2 绿 / V3 金,支持「只看 ≥V2」过滤——研究报告的可信度是分层的,UI 要让这一层可见。
- 头部固定条:课题 / 日期 / 总体证据等级 / 来源数 / 发现数。

### 3.2 来源 tab(反馈⑤)
- **卡片而非截断列表**:完整标题(可换行)+ 类型徽章(文献/代码域)+ 作者·年份 + 要点摘要。
- **主操作=打开**:文献走 URL,代码域走证据锚跳文件定位行。**「看得见打不开」是本 tab 的头号禁止项。**
- 次操作:编辑(字段行内编辑,走 docs_update)、归档、复制引用(生成 `[S-00x]` 或 BibTeX 条目,供 refs.bib)。
- **反查**:每张卡显示「被 F-00x / 报告 §x 引用」,双向可跳。
- 筛选与排序:类型 / 年份 / 被引次数。

### 3.3 发现 tab
- 按域(代码/文献)分组,V 等级徽章置顶。
- 每条:结论全文(不截断)+ 证据锚(可点)+ refs 的 S-id(可跳)+ 状态。
- 操作:确认 / 丢弃 / 编辑 / 删除。
- **状态样式区分**:`confirmed` 是**成就**不是失效,不得整条置灰(现状把终态渲染成禁用态,反馈④的直接来源)。

## 4. 交互硬契约(验收级,不可降级)

1. 任何来源都能一键打开(URL 或 file:line),不存在只能看不能开的条目。
2. source/finding 与 req/defect **同权**:可展开、可编辑、可删除、可归档;前端不得再有 kind gating。
3. 标题与结论**不截断**(卡片换行;确需省略时悬停给全文)。
4. 引用**双向**可跳:报告→来源、发现→来源、来源→被引处。
5. 空态给指引(没有来源时告诉用户怎么产生),不是一个孤零零的「(空)」。

## 5. 全文通道(反馈③,工具层配合)

用户定调:**广度分析读摘要没问题,但必须有「投喂正文也能读」的通道。**

- **现状缺口**:`read` 不支持 PDF(read.rs 无 pdf 分支);arXiv API 只给 summary;webfetch 抓 HTML→文本可用但未对 arXiv 正文做专门通道。
- **要做三件**:
  1. `read` 支持 PDF 文本抽取——用户把正文 PDF 放进 topic 目录,agent 能直接读(这是「我们给他正文他也能读」的最短路径);
  2. arXiv 正文通道:`arxiv.org/html/<id>` 优先、ar5iv 降级、PDF 兜底,取回的正文落 topic 目录留档;
  3. 来源卡标注**证据深度**:`摘要级` / `正文级`,与 V 表联动——**摘要级封顶 V1,读过正文才够 V2**(D-412 的机制化)。
- 效果:广度扫摘要、深度读正文,两者在 UI 上可区分,报告的 V 等级不再含糊。

## 7. 定调(2026-08-16 用户拍板,以下为设计约束)

1. **打开文献 = 内置 viewer**(复用既有 viewer-overlay)。不跳出应用;顺带打开的正文可存进 topic 目录,直接接上 §5 的「摘要级→正文级」升级链——这是选内置的主要理由,不只是排版偏好。
2. **research 档下 dev 视图完全隐藏**。模式感优先:研究时看不到需求/缺陷/目标/测试/git。代价(查 backlog 要切回 dev)用户已接受;若「建议登记」段需要引 R- 编号,由报告侧提供只读引用,不为此把 dev 视图放回来。
3. **来源用卡片流**。完整标题换行 + 作者·年份 + 要点摘要 + 打开/编辑/引用操作;不做表格切换(轻课题几十条量级,可读性优先于密度)。重课题上百文献时再评估是否补紧凑视图,不预先实现。
