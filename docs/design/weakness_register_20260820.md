## 二、弱项一:仓库导航效率与工具本体感知(R-310 / D-575)

评估引用的一轮真实轨迹失手清单:

```
git log directory → error
memory_search → 召回不相关 M-006
read 读错 memory 路径
symbols 查不存在的 coordinator.rs
read 不存在的 invariant.rs
read lib.rs 范围错
insert 漏 path 参数
```

七次失手都恢复了、没有造成后果——问题不在恢复,在**认知预算耗在操作 harness 而不是解决软件问题**。评估的图示:模型脑力同档,差在 tool proprioception(工具本体感知)。这个差距的两个可修面:

1. **工具侧自愈(D-575)**:失手时工具只回裸错误,不给最近邻候选/合法范围/必填参数点名——每次失手至少多付一轮调用。修好后失手从「再猜一次」变「一次纠正」。弱模型(自举档)收益更大,符合「弱模型也能照着走」的取舍准绳。
2. **供给侧地图(R-310 批3)**:模型对仓库结构靠 grep/glob 试错重建,代码地图(crate→模块→公共符号)是 Claude Code/Codex 都有的标配供给。形态(注入 repo map vs 工具化按需查)必须先过 token 成本核算——这直接联动 §四的减负方向,不许为修导航反而加重上下文负载。
3. **度量先行(R-310 批1)**:失手率(不存在路径/越界范围/漏参数/空搜索/权限拒绝 分类)先出基线,批4 用同口径复测,避免「感觉变好了」。

memory_search 召回不相关 M-006 不归本条:INDEX 描述串号毒化 FTS 已登记 D-568,冗余治理在 R-308。

## 三、弱项二:验证闭环 execution tail(R-311)

评估的判断:前 80%(迁移不变式定义、authority 划分、修改面限定)已是高级工程师水准,但「4 小时 migration 一次性完整交付」仍会押 Codex——不是分析更聪明,是 execution tail reliability 更有证据:

```
实现 → compile → 失败 → 诊断 → 修 → targeted tests → full regression
→ grep invariant → diff review → requirement acceptance → commit
```

kanzei 已有的:13 步 verify 门禁、关闭前逐条验收对照(§1.25)、source_test_gate。缺的两块:

1. **不变式停在文本**:设计冻结字段写「正常 typed run 不再追加 conversation.updated」这类不变式,但没有任何机械检查在 finalize/close 时替模型复查——恰好本轮 R-242 的 D-572 就是「不变式写了、代码里还剩两处违反」的现场。R-311 批1 让冻结不变式可登记为机器可跑断言(grep 模式/测试名/脚本),关闭时自动执行、失败拒关。
2. **收尾链无统计**:每条目是否走完收尾链没有按条目留痕聚合,「最后一公里稳定性」永远只能靠印象辩护。R-311 批2/3 把收尾链完成度、门禁拒绝、返工次数做成滚动报表——这同时是评估点名缺失的「连续几十个 requirement 的长程统计证据」的载体。

failure recovery 不单开条目:恢复纪律已由 verify 重试、shadow gate 回退、D-575 自愈报错分头覆盖,先看 R-311 批3 的统计再决定要不要专项。

## 四、用户新增方向:给 Agent 减负(R-312)

用户观察(2026-08-20):上下文压缩管理实际上有点问题,包括导航的问题;**很多负载都维护到状态机里了**,应该思考怎么给 agent 减负。

现状盘点(file:line 为 2026-08-20 dev):

- 注入面已有克制设计:req/defect 全量队列**刻意不常驻**,引擎只注一块 resolved-control-state(profiles/dev.rs:324-336);ideas 只注计数+标题(:160);memory 只注 INDEX 行+预算内 preference 全文(:219);conventions 全量注入是有据决策(D-201,:189-200)。
- 负载在哪(待批1 账单核实的假设):
  1. **条目自由文本字段只增不减**——进展/对账/停车按批追加,R-242 进展字段已数百字,`req get` 每次全量背回;字段维护本身(每批写进展、对账、停车理由、取活依据)是模型侧持续支出。
  2. **锚点腐烂**——条目里的 file:line 随代码演进失效,模型重新推导定位,导航负载被状态机放大而不是吸收。
  3. **压缩与注入不协同**——harness 注入块(conventions/memory-index/control-state)是每轮可机械重取的事实,压缩纪要不该为它付预算;context_compaction.md 的 L0 prune 只清工具输出,没覆盖注入面。压缩引擎本体的缺陷(D-573 CLI 压缩事务)走各自条目。

方向假设(四个,R-312 批2 逐个出方案与取舍,批1 先用账单证明哪个占比最大):

1. **机器可代填字段**:observed_head/recorded_at 已是机器写;进展里的机械部分(测试记录号、提交号、批次推进)也由引擎代写,模型只写判断性内容。
2. **注入分层**:当前 WIP 条目全文+依赖闭包,其余条目给索引行——把「刻意不常驻」从队列级细化到字段级。
3. **历史沉档**:进展/对账超过当前批次的旧段落自动折叠沉档,`req get` 默认当前批次视图,全文按需取。
4. **压缩协同**:可机械重取的注入块打标,压缩时机械剥离不进纪要;file:line 锚点腐烂的对策(锚点校验/符号锚点)一并评估。

纪律:R-312 本条不改代码(先计划后自举);先测量再动刀,账单没证明失衡的不动——尤其 conventions 全量注入(D-201 的教训是「被截断的规则没人遵守」,瘦身方向是精简规范本身,不是引擎悄悄截断)。
