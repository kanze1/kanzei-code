## 背景与问题

2026-08-21 一轮外部架构评估对 harness 提出七点质疑。评估者的核心论点是:
本仓把**大量 intelligence 放在 harness 侧**,这在弱模型时代是优势,在强 Agent 模型
时代未必——`harness 的保守规则可能成为模型能力的上限`。

七点原始质疑与用户逐点定调:

| # | 质疑 | 用户定调 | 落点 |
| --- | --- | --- | --- |
| 1 | Harness Tax:每个行为都穿过大量 infrastructure,小任务显得重 | 按复杂度路由**有必要**,但**不应该机械** | R-322 |
| 2 | 牺牲了模型的聪明:该并行的、该停的、该总结的,harness 替模型决定了 | 提供底层工具 + **一层抽象层**,让模型去编排 | R-323 |
| 3 | Determinism 换掉了最大并行度 | **算缺陷**,不算决策 | D-661 |
| 4 | Event Sourcing 让小改动变大改动 | 系统级 loop 之外**要有简单 loop**;结伴=有人监督→控制可以轻,重控制是为了监督**过夜自主开发的信息熵增**;现在区别不够明显,**决策点要呈现给用户** | R-322 |
| 5 | Managed Documents 造成 Tool Explosion | **算缺陷**,不算决策 | D-662 |
| 6 | Memory Control Plane 复杂度增速可能高于收益 | **暂时无法确定**,挂起观察 | 见 §TODO |
| 7 | Auto Run 的双控制器问题:谁拥有最终控制权 | **决定权交给模型** | R-322 |

## 目标与非目标

### 目标

1. 把「门禁强度」从**隐含在 agent 人格里的副作用**提升为**一等显式维度**,
   与人格解耦、对用户可见、可按模式取不同默认值。
2. 收回引擎对**任务是否完成**的否决权,交还模型;引擎只保留**资源类**兜底。
3. 为模型提供声明式的编排通道(先落并行分组),引擎从「独裁调度」退为「安全校验」。
4. 修掉两条被判定为缺陷的实现问题(D-661/D-662)。

### 非目标

- **不**回退「判定下沉引擎」这一基线。规则仍然写在代码里,不回到可编辑提示词
  (D-120/D-128/D-163 的教训不因本轮调整而失效)。变的是**哪些判定属于引擎**,
  不是**判定写在哪里**。
- **不**削弱结果侧托管围栏、权限硬门禁与事件真源。这三样与「模型自治」正交:
  它们约束的是**副作用边界**,不是**任务判断**。
- **不**引入第二套开关体系。强度是**一个**枚举,不是 N 个布尔值。

## 讨论摘要

评估把两件事混在一起谈,拆开后结论不同:

- **「规则写在哪里」**:引擎侧。这条有证据(D-120/D-128/D-163 三次现场),不动。
- **「哪些事该由引擎判断」**:分情况。可拆成两类——

| 判断类型 | 举例 | 归属 | 理由 |
| --- | --- | --- | --- |
| **任务判断** | 任务完成了吗、下一步做什么、这两个调用能不能并行 | **模型** | 需要语义理解;引擎只有工具名和锁键,信息量本就不足 |
| **资源判断** | 限流了吗、连跑多少轮了、真实状态还在不在变、上下文超线了吗 | **引擎** | 与语义无关,纯机械可判定;且无人监督时没有第二个判断者 |

现行 `auto_run` FSM 的十种停止原因里,只有 `NoAction`/`Nudge` 属于任务判断,
其余(`AllBlocked`/`BacklogEmpty`/`MaxRounds`/`RepeatedFailure`/`FatalError`/
`RateLimited`/`ZeroOutput`/`Paused`/`StopAfterRound`)都是资源判断或用户意图。
所以 #7 的落点很窄:**只需要交出 `Nudge` 这一条**。

`ZeroOutput`(D-583)看起来像任务判断,实则不是:它比对的是 (HEAD、worktree hash、
tracker 文档内容) 的真实签名,不解释语义,只回答「磁盘上还在不在变」。无人监督时
这是唯一的失控兜底,保留。

## 候选方案

### 方案 A:按 agent 人格继续隐式分档(现状)

差异只落在系统提示词与 `auto_allowed` 的二值条件。
- 优点:零改动。
- 缺点:用户看不见自己选了什么;新增机制时只能再长一个布尔开关
  (`phase_pipeline_enabled` 已是第二个);无法表达「结伴但要重门禁」。
- **不采用**(正是 #4 指出的问题)。

### 方案 B:按任务复杂度自动路由

轮首估算复杂度(文件数/预计步数/条目复杂度字段),自动选强度。
- 优点:用户零操作。
- 缺点:**机械**。用户明确否决:「根据复杂度路由是有必要的,但是不应该机械」。
  且复杂度的真实判断者是模型,不是引擎的启发式。
- **不采用**。

### 方案 C:显式强度枚举 + 模式默认值 + 模型可申请 + 用户可见(选定)

- 强度是一等概念 `HarnessIntensity { Paired, Autonomous }`,由**模式**给默认值;
- 模型在轮内可以**声明**(完成、并行分组),引擎按**单调收紧**规则校验;
- 决策点在界面呈现,用户随时可覆盖。

复杂度路由通过「模型声明」间接实现——模型知道这次是改一个 CSS 还是重构一个子系统,
它来说,引擎不猜。这满足了「有必要但不机械」。

## 最终方案

### 一、门禁强度(R-322)

```rust
pub enum HarnessIntensity {
    /// 结伴:用户在场监督。模型自治优先,引擎只保留资源类兜底。
    Paired,
    /// 自主:无人监督。全套门禁——目标是抑制长时间无人值守的信息熵增。
    Autonomous,
}

pub struct IntensityPolicy {
    /// 引擎能否在模型本轮无实质动作时追加推进指令(Nudge)。
    pub engine_nudge: bool,
    /// 冗余机械提醒([冗余提醒] 就地追加)。
    pub redundancy_hints: bool,
    /// 每关闭 N 条插入的只读验收核查轮。
    pub verify_rounds: bool,
}
```

| 机制 | Paired | Autonomous | 归类 |
| --- | --- | --- | --- |
| 模型声明完成 → 停 | **是** | **是** | 任务判断,永远归模型 |
| 引擎 Nudge | 否 | 是 | 任务判断,仅无人监督时借给引擎 |
| 冗余提醒 | 否 | 是 | 用户在场时自己就看得见重复 |
| 验收核查轮 | 否 | 是 | 用户在场时由用户验收 |
| 失败召回注入 | 是 | 是 | 纯增益,不占决策权 |
| 资源类停止(限流/致命/连数/ZeroOutput/backlog) | 是 | 是 | 资源判断,两档都保留 |
| 权限硬门禁 / 托管围栏 / 事件真源 | 是 | 是 | 副作用边界,与自治正交 |

### 二、模型停机权(R-322 / #7)

新增 `AutoStopReason::ModelDeclaredDone`。判定顺序里插在**用户意图与资源兜底之后、
任务判断之前**:

```
backlog → auto_allowed → halted → paused → stop_after_round → max_rounds
  → round_failure → 【model_declared_done】→ no_action/Nudge → zero_output
  → verify_round → Continue
```

模型的声明通道:`work` 工具新增 `handoff` 动作。选 `work` 而不是新工具,是因为
D-662 已经把「工具膨胀」判成缺陷——`work` 本就是取活/工作编排的抽象面,
循环控制归它语义自洽,且不扩大模型的工具选择面。

声明的采集走**事件流**,与 D-654 同一套路(`ToolStart` 登记意图 → `ToolEnd` ok
才计数),不扫消息历史:轮中上下文压缩会结构性删短消息列表,切片会错位。

### 三、编排抽象层(R-323 / #2 / D-661)

分两步,本轮只做第一步:

1. **D-661 先修**:`build_tool_execution_waves_with` 从「顺序扫描遇冲突即封波」
   改为**冲突前驱层级调度**——每个调用的最早可入波 = 所有更早冲突前驱所在波 + 1,
   从该波起找第一个未满的波。顺序遍历 + 最早可用波,确定性保持。

   **不是 first-fit 装箱**(方案评审时否决):朴素 first-fit 会把调用塞进比其冲突
   前驱更早的波,等于把两次冲突操作颠倒过来。`ToolConcurrency::conflicts_with`
   表达「不能同时跑」而它蕴含「顺序有意义」——同树两次 `WorktreeWrite` 是两次写,
   `Shared` 与 `WorktreeWrite` 是读与写,先后颠倒都换结果。因此必须保住不变式:

   > 对任意 `i < j`,若 `calls[i]` 与 `calls[j]` 冲突,则 `wave(i) < wave(j)`。

   评估者原始举例(`A↔B`、`B↔C` 冲突,`A` 与 `C` 不冲突,期望 `[[A,C],[B]]`)
   **不成立**:它要求 `C` 跑在 `B` 之前,而两者冲突。真实见证用例换成
   `[A,B,C,D]` + `A↔B`、`C↔D`:旧实现 `[[A],[B,C],[D]]` 三波,新实现
   `[[A,C],[B,D]]` 两波,且不颠倒任何冲突对。
2. **R-323 后做**:模型可在工具调用里声明并行分组,引擎以 `ToolConcurrency`
   冲突检测作为**单调收紧**的安全网(与 tool_pipeline 的 Guard 同一原则:
   声明是 policy 层提议,冲突是 guard 层否决,只收紧不放宽)。

### 四、决策点呈现(R-322 / #4)

强度必须在界面上是一个**独立可见控件**,不是藏在 agent 下拉框里的副作用。
用户随时可覆盖模式默认值。

## 技术选型与取舍

| 决策 | 选择 | 取舍 |
| --- | --- | --- |
| 强度载体 | 枚举而非 N 个布尔 | 失去逐项微调,换来「没有两个开关可以互相矛盾」(沿用 phase_pipeline 的精神) |
| 停机权 | 模型声明即终止 | 模型误判「完成」时无人纠正——但用户在场(Paired)本就会纠正,无人值守(Autonomous)有 ZeroOutput/MaxRounds 兜底 |
| 声明通道 | 扩展 `work` 动作 | 不新增工具(D-662),代价是 `work` 的 schema 继续变长 |
| 采集方式 | 事件流 | 与 D-654 一致;不用消息切片(压缩会错位) |
| 调度改造 | 冲突前驱层级调度 | 在「保住冲突对顺序」的约束下已是最优;放弃 first-fit 装箱那种更高并行度,因为它靠重排冲突操作换来,是换语义不是提速 |

## 实施边界与调用方

- `crates/kanzei-harness/src/auto_run.rs`:强度枚举、策略表、`ModelDeclaredDone`、
  判定顺序。**纯逻辑,无 IO**,单测是权威。
- `crates/kanzei-tools/src/work/tool.rs`:`handoff` 动作。
- `crates/kanzei-core/src/runner/tool_exec.rs`:`build_tool_execution_waves_with` 装箱。
- `crates/kanzei-app/src/run/events/mod.rs`:`MetricsSink` 采集 handoff 事件。
- `crates/kanzei-app/src/run/coordinator.rs`:把强度与声明送进 `AutoRunCtx`。
- `crates/kanzei-app/ui/`:强度控件与回显。

**不动**:权限 Ruleset、托管围栏、事件存储 schema、记忆控制平面。

## TODO 与后续风险

- **【B1 已知缺口】轻档 loop 目前不可达**:`decide()` 的 `auto_allowed` 检查排在
  强度策略之前,而 `auto_allowed` 要求 `agent == "dev"`,于是 `Paired` 档永远先
  `Stop(ProfileMismatch)`——`policy.engine_nudge` 与 `policy.verify_rounds` 在生产
  路径上还观察不到,只有 `redundancy_hints`(经 `RunnerConfig`,不走 `decide()`)真正
  生效。用户「系统级 loop 之外要有简单 loop」的诉求要落地,必须允许结伴档在用户
  显式开启鞭挞时以轻控制续跑,这会改动 R-199 的判据与 `08-compose.js` 里
  「勾选鞭挞即强制切到 dev-auto」的逻辑。属产品决策,B2 待用户拍板后执行。

- **#6 Memory 复杂度(挂起)**:评估指出记忆控制平面可能让可调试性下降——
  「为什么今天它突然做了这个错误决定」的答案可能是「召回了一条六天前的错误 memory」,
  于是确定性 harness 之上重新引入了大的随机成分。用户定调「暂时无法确定」。
  **观察口径**:R-166 的 F(m) 聚合已在库内(`memory_eval_agg`),
  但离线回放成本高、样本稀疏。在攒够样本前不扩张记忆机制,也不删减。
  重议触发条件:F(m) 样本数达到可判定量,或出现一次可归因到错误召回的现场。
- **#5 D-662 的解法未定**:本文只登记缺陷,不预设方案。可能方向包括合并
  tracker 四件套为单一 `tracker(kind, action)`、或把托管写通道收敛为
  `doc(path, op)` 由引擎按路径分派。改动面大且触及托管围栏的白名单
  (`managed_fence.rs` 的 `MANAGED_WRITERS`),须单独设计。
- **强度与 phase_pipeline 的关系**:`phase_pipeline_enabled` 是现存的第二个开关。
  本轮不合并(避免一次动太多),但 R-322 落地后应评估把它并入强度维度,
  否则「不设第二个开关」的原则名存实亡。
