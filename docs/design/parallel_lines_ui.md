# 任务级并行的前端：并行视图设计

- 日期: 2026-08-11
- 状态: 方案待拍板
- 关联需求: R-184(本文主体) R-179 R-177 R-182 R-185 R-174 R-133 R-030
- 关联缺陷: D-267 D-268 D-263
- 依据: 2026-08-11 用外部脚手架跑通的一轮真实任务级并行（三条独立进程/worktree/分支，两条完整交付、一条并证伪了缺陷自身的次因猜测，合并零冲突、合并后全量门禁全绿）。**本设计的每一处字段与流程都来自那一轮里操作员真正需要而当时没有的东西**，不是凭空设想的界面。

## 0. 一句话

把「分支干、合并、冲突检测解决、文档一份唯一」这套口径，做成**一个操作台**：一屏看到 N 条线在干嘛、谁和谁会撞、以及把每条线收回主干的固定流程。

## 1. 为什么值得做进 kanzei（而不是继续用外部脚手架）

2026-08-11 那轮是用外部 `claude` 进程 + PowerShell 脚本跑的。它能出活，但操作员付了三笔代价，**每一笔在 kanzei 里都不存在**：

| 外部脚手架的代价 | kanzei 里为什么没有 |
|---|---|
| **看不见**：`claude -p` 输出全程缓冲，实测一条线在日志 **0 字节**时已经提交了代码并继续跑了 40 分钟 | kanzei 拥有 runner，`RunEvent`（`ToolStart`/`TaskProgress`/`ToolEnd`）是**实时流**，不需要解析日志 |
| **判活性只能猜**：任务记录与 OS 进程脱钩，操作员据此误判一条活线已死、去动了它的工作树（D-263 的形状，当晚真实发生） | `ProcessHandle` 就是生命周期真源，活性不需要推断 |
| **收活全手工**：读报告 → 读 diff → 跑门禁 → 合并 → 回写 tracker，五步全靠人记 | 门禁、worktree 四命令、tracker 工具 kanzei 全都有，只差把它们串成一条流程 |

结论：这个界面的价值不在"好看"，在于**把当晚那三笔代价一次性消掉**。

## 2. 落点：新增第 9 个主视图「并行」

`data-view="lines"`，与 workspace / documents / files 等同级。

**为什么是主视图而不是面板**：并列看 N 条线要横向空间。现有三处都不合适，而且各有各的职责，**不重复也不替代**：

- **线页签徽标**（R-179 内容③）是**单线**视角——你切到哪条看哪条；
- **活动面板 `#bg-panel`/`#bg-list`**（R-173/R-174）是**单进程内**视角——一条线内部的子代理与工具轨迹；
- **侧栏 `#worktrees-section`** 是**静态清单**——有哪些树，不含运行态。

本视图是**跨线**视角。三者构成"树 → 线 → 线内"三层，各管一层。

**考虑过并否决**：塞进 `workspace` 视图。它的定位是"统一查看项目、对话、运行状态"——那是**纵览**；并行视图是**操作台**（要开线、要停线、要合并）。混在一起两边都变钝。

侧栏 `#worktrees-section` 改为本视图的**入口**（点条目跳过去），不再并列维护两套工作树 UI。

## 3. 三个区，对应操作员的三个动作

```
┌─ 开线区 ────────────────────────────────────────────┐
│ [开线 ⑂]  选条目 → 预测文件面 → 与在跑线求交 → 起  │
│ 全局态：3 条在跑 · 共享 target 53GB · 本轮 128k tok │
├─ 泳道区 ────────────────────────────────────────────┤
│ ▸ D-262 kill_tree      par/d-262   跑着 · bash      │
│ ▸ D-261 原子写并轨     par/d-261r  跑着 · cargo     │
│ ▸ D-233 文件视图卡顿   par/d-233   完成 ✓           │
├─ 冲突带 ────────────────────────────────────────────┤
│ ⚠ D-261 ✕ D-233  共同改动 kanzei-tools/src/files.rs │
│ 文本层已检查 · 语义层未检查（需人读 diff）          │
└─────────────────────────────────────────────────────┘
```

### 3.1 泳道卡片的字段

**直接照搬当晚实际用过并验证有效的那套**（外部脚手架的 `status.ps1`），不多不少：

| 字段 | 数据源 | 为什么必须有 |
|---|---|---|
| 认领条目（`D-262` + 标题） | 开线时绑定 | 一屏答"这条线在干哪件事" |
| 分支 / worktree 路径 | `git worktree list --porcelain`（R-177 内容③已定为真源） | 收活时要用 |
| 状态 | `ProcessHandle` + 最近 `RunEvent` 时刻 | 见下方状态机 |
| **当前工具名** | `ToolStart` 实时 | 当晚最想要而没有的一个字段——它是"卡住 vs 在长构建"的唯一判据 |
| 轮数 / 已改文件数 / token / 耗时 | `RunEvent` + `episodes` + `git diff --name-only` | 已改文件数是冲突带的输入，顺带显示 |
| 单条停止 | R-174 已备的 per-role `CancellationToken` 改法同源 | 一条跑偏不该停整批 |

展开后三个页签：**transcript**（复用 R-174 的）、**diff**（复用 `06-activity.js` 的 `buildDiffTree`/`renderDiff`，R-133 已 done）、**报告**（线的最终产出文本）。

### 3.2 状态机与判据

```
起线 → 跑着 → 完成 ✓
           ↘ 失败 ✗
           ↘ 疑似卡住 ⏳（可回到"跑着"）
```

判据顺序**必须**是：①`ProcessHandle` 活性 → ②最近 `RunEvent` 时刻 → ③worktree 源码 mtime。

**不得只用"日志/事件多久没动"判死**。当晚正是这个误判让操作员去动了一条活线的工作树。「疑似卡住」只是**提示**，不触发任何自动处置（不自动停、不自动回收）。

### 3.3 冲突带

**算法（第一版就这么简单）**：每条线的改动集 = `git diff --name-only <merge-base>...<branch>` ∪ 未提交的 `git status --porcelain`；两两求交；非空即画一条告警。

**为什么不用 `merge-tree` 两两预检**：N 条线是 N² 次，成本不划算，而且它回答的是"合并会不会冲突"——太晚了。文件集求交回答的是"**现在**是不是在往同一个文件写"，这才是要提前知道的。`merge-tree` 留给收活流程里真正要合的那一次。

**告警必须早于任何合并动作**（R-184 验收⑥）。点开下钻到"哪两条线 / 哪些文件"。

### 3.4 诚实：语义层不假装

冲突带旁常驻一行 **「文本层已检查 · 语义层未检查」**，不可关闭。

理由：git 只做文本层。A 把某签名重构成形态①、B 按形态②写完，两边测试各自都绿，合并干净，**语义已经坏了**。R-182 已明确不做语义撞车的事后检测。界面**不得**让"冲突带是空的"读起来像"可以安心合并"。

## 4. 收活流程：把当晚的五步固化成五格

```
① 读报告  →  ② 人读 diff  →  ③ 跑门禁  →  ④ 合并  →  ⑤ 回写 tracker
   （人）      （人·必须显式确认）  （kanzei）   （kanzei）   （kanzei）
```

- **②不可跳过、不可自动**：必须点一次"我已读过 diff"才能进③。这是语义层唯一的防线，做成必经的一格而不是提示。
- **③门禁由 kanzei 跑**：fmt / clippy / test / 前端冒烟。当晚实测**不能信线自己说的绿**——一条线交付时没跑 `cargo fmt`，三处违规是操作员跑门禁才发现的。
- **④合并**用现成的 `worktree_merge`（含 `merge-tree --write-tree` 预检），按 N2 定案保持 `--no-ff`。合并后**再跑一次全量**：两条线各自绿 ≠ 合起来绿。
- **⑤回写 tracker** 走 tracker 工具落**主根**一份。线全程不碰 `.kanzei/**`——当晚实测两个 worktree 相隔 10 秒各登记一条缺陷，**都拿到 `D-267`**，因为它们锁的是两个不同的文件。验收未全达成的必须保持 `open` 并写清哪条没成。

## 5. 开线区与耦合预检（依赖 R-185）

开线时选条目 → 显示**预测文件面**（从条目正文里出现的路径 + `refs` 互指导出，就是当晚人工做的那件事）→ 与**在跑线**的改动集求交 → 有交集则**明确拦下并说明是哪条线、哪些文件**，而不是给个可无视的警告。

当晚人工避开的四类耦合，是这一步的验收样例：

1. 两条目共用同一文件（D-260 与 D-261 残余共用 `atomic_file.rs`/`test_record.rs`）
2. 撞正在 `doing` 的需求（D-247 撞 R-178 批4 的 `settings.rs`）
3. 目标是 tracker 文件（D-259 要改 `tests-archive.md`）—— 根本不能并行
4. 某条的**部分**修复方向撞别人（D-233 的③④要动 `files.rs`，那是 D-261 残余的目标）

**一条重要教训**：预测文件面要从**验收**推，不是从**根因**推。当晚给线 A 的允许集是按根因文件（`shell.rs`）给的，而 D-262 验收③本来就要求改 `background.rs`/`bash.rs` 两条路径——**是提示词错了，不是线越界**。

## 7. 明确不做

- 图形化 DAG / 画布式线管理（与 `deep_parallel_dev.md` §2.3、R-111 的克制一致）。
- 自动解冲突、自动重新适配。
- 语义撞车检测（R-182 已明确不做；本设计只负责**不掩盖**它）。
- 跨线自动任务分派——线由用户手工开。

## 9. 验收（并入 R-184）

R-184 既有验收⑤⑥⑦⑨⑩ 覆盖本设计的泳道与冲突带，另补三条：

1. **状态机三级判据有反证测试**：构造"进程活着但事件长时间不动"的场景，界面显示「疑似卡住」而**不**触发任何自动处置；构造"进程已退出但无终态"的场景，显示为失败而非卡住。
2. **收活②不可绕过**：未点"已读 diff"时③④⑤ 全部不可达，有冒烟断言；断言被删则测试变红。
3. **「语义层未检查」提示不可关闭**：有断言锁死它在冲突带为空时**同样**显示。
