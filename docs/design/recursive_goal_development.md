# 长期维护与开发模式：递归目标与证据驱动的工作图

状态：已实现核心纵向链路，进入本地全量验收与发布门禁。本文同时记录产品合同、代码责任和实测边界。

## 1. 产品目标

用户提供一个可以暂时模糊的愿望。系统保留原文和边界，逐步建立可验证的目标，发现未知，调研、设计、实现、验证，并根据新证据调整拆分。一次对话结束不丢失工作；没有可推进事项时等待真实变化，不为维持运行制造任务。

“费曼式”在此表示操作方法：解释目标和当前理解，指出无法解释或缺乏证据的部分，将缺口变成有产物的工作，再根据结果重新解释。解释流畅不构成验收证据。

模式面向同一项目内持续的开发和维护。当前结伴开发的授权边界保留；普通聊天不会因为出现目标语句自动开启长期执行。已有自主推进控制器负责启动、暂停、停止、预算和续跑，不增加第二个循环控制器。

## 2. 对象与所有权

| 对象 | 责任与真源 |
| --- | --- |
| 用户委托 / Outcome | 原始愿望、来源、范围和阶段验收；沿用项目需求文档真源 |
| 工作节点契约 | 目标、类型、归属、依赖、验收、未决问题和当前解释；扩展已有 Work Unit 契约，不创建独立任务数据库 |
| 工作事件 | 创建、拆分、修订、领取、检查点、证据与关闭；沿用 core 的 append-only work_events |
| 当前投影 | 重放事件得到的节点当前状态；沿用 work_surfaces，可重建 |
| 调度视图 | 由当前投影、依赖、归属、占用与 Outcome 状态推导；tools/work 是唯一调度入口 |
| 证据 / 产物 | 文件、测试、实验、来源与运行回执；节点保存引用及适用版本，不把产物全文复制入树 |
| 用户界面 | 目标树、当前工作、阻塞原因、证据和变更历史；读取上述事实，不自行推导另一套关闭规则 |

统一节点不等于把契约和执行历史混为一体。一个节点保留当前契约；多次执行、探索与修订仍通过独立事件表达。技术标识 WorkUnit 和 R-xxx/Wn 保持稳定，UI 使用“工作节点”。外层 Requirement 继续承接原始用户委托和已有交付合同。

节点类型：goal、requirement、defect、research、design、documentation、verification。类型与深度独立，任何类型都可拆分。旧单元缺少类型时按 requirement 解释。功能/非功能分类与这些工作类型是不同维度。

新工作中的缺陷和调研使用同一节点事件、依赖和验收路径。历史 R/D 台账通过既有队列保留，不批量改号或伪造迁移完成。历史条目转入新执行模型必须显式绑定来源，避免两个对象同时拥有同一工作的当前状态。

## 3. 树与依赖图

归属 parent 回答“为哪个目标服务”，每个节点最多一个父节点，归属不得成环。外层 Outcome 是树根的用户视角；同一 Outcome 可以有多个顶层节点。

depends_on 回答“需要哪个已完成结果”。允许跨分支引用同一真实结果，不复制共享调研。依赖不得缺失、自指或形成环。

完成顺序必须同时检查显式依赖和父节点等待子节点的隐式关系。例如父 A 等子 B，B 又依赖 A，会永久死锁，写入时拒绝。子节点还必须遵守祖先的前置依赖和暂停/阻塞约束，不能通过向下拆分绕过前置。

子节点用 covers 指向父契约的验收条款。拆分可以逐步补齐，不要求一次规划完整树；父节点最终收口时必须解释其全部验收如何成立。被取消的分支不算成功覆盖。

## 4. 递归与准备度

每次决策只处理当前前沿，不预先展开整个项目。

1. 当前目标缺乏理解或含未决问题：先解释缺口，建立 research/design/verification 节点。
2. 工作不可在一次有界执行内独立验收：按产物、接口或可验证行为拆分。
3. 输入、范围、前提和验收已明确：执行当前叶节点。
4. 子节点结束：重新检查父契约，补充解释、消除已解决问题，或根据新证据继续拆分。
5. 父节点自己的组合验证通过：登记父级证据并完成。

对话轮数和代码行数只作估计，不是强制阈值。不能把“学会 memory”登记成没有输出的工作；可以登记“比较偏好保存/纠正方案，形成支持选型的结论与来源”。

调研允许得到否定或不可行结论。它是否完成取决于原调研验收，而不是是否支持原假设。结论不充分时留下明确问题，不能把“写了报告”当作问题已解决。

## 5. 状态、拆分和修订

沿用 ready → active → verifying → done；blocked 和 superseded 保留现有意义。

规划、执行和父级收口是从契约与子节点推导的下一步动作，不扩张成与上述生命周期竞争的另一套状态机。

拆分是一个原子操作：检查父版本、验证子契约和图、创建子节点、记录拆分原因、释放父占用。写入失败不能留下半棵树。父节点在子节点工作期间保持未完成，不继续占用开发 WIP。

修订必须记录原因并校验调用方观察到的版本。节点身份和归属不能通过普通修订偷偷改变。目标、验收、依赖或解释改变后，原证据不直接支持新契约；原事件保持可审计。已完成节点保持不可变，后续问题通过新的缺陷或替代工作表达。

父节点仍有未终态子节点时，不允许完成或整体废弃以隐藏剩余工作。superseded 与 done 必须在依赖、覆盖和统计中区分；依赖完成只接受 done。

## 6. 验收与证据

叶节点需要覆盖自己的每条验收。父节点还需要必要子工作结束以及自身的组合验收，不能因子节点全部变绿而自动完成。

实现节点验证行为；缺陷节点保留复现和修复验证；调研节点回答具体问题并给出来源/限制；设计节点交付接口、约束和取舍；文档节点以读者能完成的操作验收；验证节点保留输入版本、命令/路径、结果与适用范围。

存储层验证身份、版本、关系、状态和非空引用；工具层验证文件或测试引用真实存在及其关联；语义审查仍需判断证据是否真正支持条款。通过窄测试不能证明整个产品完成。

## 7. 调度、恢复和上下文

继续使用 work next / claim 和每条线一个活动工作。父节点等待子节点期间，选择依赖满足的子节点；所有子节点终态后把父级收口重新交给模型。未决问题对应规划动作，不假装成为可实施任务。

提供当前节点、有限祖先目标/边界、依赖产物摘要、直接子节点状态、最近检查点和本节点验收。完整历史按需读取。所有截断必须可见，并提供取回完整契约的入口。`work next` 的 `context_omissions` 列出裁剪位置和原始数量；`work get_unit` 返回完整契约及事件。

自动队列状态使用同一 `resolve_work_selection` 结果，并传入当前工作线和优先级。进展签名纳入节点契约、验收证据和终态；领取、检查点、时间戳和重试验证本身不算新成果。数据库读取失败显式报告未知并暂停零产出比较，不能误报已经清空。

每次恢复先重读权威投影与实际产物，不能凭上一轮摘要重做已完成工作。版本冲突返回明确纠正，不静默覆盖。错误、等待、暂停、取消和完成分别展示。

## 8. 长期维护

有限阶段目标可以关闭，长期维护责任持续存在。用户反馈、回归失败和依赖变化成为有来源的新节点；新节点必须能说明如何服务原始委托。

没有就绪节点时沿用控制器的等待/停止机制，保留目标和恢复位置。未来定时触发仍通过现有 schedule 入口，不创建后台自旋或靠 sleep 轮询。暂停后不自动重启。

进度优先报告已验收能力、当前工作、关键缺口和待外验，不以动态变化的节点总数承诺固定完成百分比。根节点成功不能由“所有事项已归档”推出。

## 9. 接口与界面

扩展 work create_unit 的节点类型、归属、覆盖和问题字段。新增原子 decompose、带版本的 refine 与 graph 查询，保持已有 claim/checkpoint/verify/evidence/complete 单一路径。CLI 与模型工具调用同一服务。

目标树展示节点类型、状态、当前动作和直接阻塞；详情展示原始来源、验收、解释、未决问题、产物和变更原因。跨分支依赖单独呈现，不能混成父子线。用户可以暂停、继续、调整目标和添加反馈，操作仍走现有权限与运行归属。

“长期维护与开发”替换面向用户的“自主推进”模式名称；保留内部协议标识和历史枚举。首次输入愿望时由模型将其登记为 Outcome 与首个规划节点；模式切换本身不能默默创建任务。

## 11. 实现映射与接口示例

| 层 | 代码入口 | 边界 |
| --- | --- | --- |
| 核心契约 | `crates/kanzei-core/src/store/work.rs`、`work/graph.rs` | 事件投影、原子事务、版本校验、关系与关闭不变量；通过 core 公开类型/SessionStore 服务调用 |
| 执行选择 | `crates/kanzei-tools/src/work.rs`、`work/context.rs` | 当前前沿、工作线所有权、需求/缺陷优先级、规划与整体收口指导 |
| 写入入口 | `work/tool.rs`、`work/evidence.rs` | 工具参数、所属 Outcome、领取、证据文件/测试记录、同批子节点编号 |
| CLI | `crates/kanzei/src/cli/work.rs` | 与模型工具共用服务；JSON 文件承载复杂契约 |
| 自动续跑 | `tracker/scheduling.rs`、`kanzei-app/src/auto_run.rs` | 使用当前线选择结果；真实进展签名；复用既有控制器 |
| 界面 | `kanzei-app/src/docs.rs`、`ui/26-work-tree.js` | 服务端准备度投影；可折叠树、验收依据、刷新状态保持 |

创建首个目标使用已有 `work create_unit`，附加 `node`：

```json
{"action":"create_unit","requirement_id":"R-001","objective":"交付可纠正偏好的个人 agent","acceptance":["用户能查看并纠正偏好，后续回答使用纠正结果"],"base_revision":"实际代码版本","node":{"kind":"goal","questions":["偏好如何保存与纠正？"]}}
```

读取 `get_unit` 的 `source_sequence` 后原子拆分：

```json
{"action":"decompose","id":"R-001/W1","expected_sequence":2,"reason":"先明确偏好纠正合同，再实现","children":[{"key":"research","objective":"比较偏好保存与纠正方案并给出结论","acceptance":["报告回答保存、纠正、生效与来源问题"],"node":{"kind":"research","covers":["用户能查看并纠正偏好，后续回答使用纠正结果"]}},{"key":"implementation","objective":"实现并验证所选偏好纠正方案","dependencies":["@research"],"acceptance":["偏好纠正场景通过"],"node":{"kind":"requirement","covers":["用户能查看并纠正偏好，后续回答使用纠正结果"]}}]}
```

`expected_sequence` 必须来自实际读取；示例值不能照搬。`@research` 仅在这一批拆分中解析为真实节点 ID，落库后只保存真实 ID。研究仍复杂时，可以对研究节点继续使用相同接口。

CLI 对应 `work decompose R-001/W1 --expected-sequence <n> --reason <原因> --children-file children.json`。`work refine <id> --expected-sequence <n> --reason <原因> --refinement-file contract.json` 接收从 `get_unit.contract` 修改的完整契约；`work graph --requirement R-001` 查询节点和准备度。已有 `claim → verify → evidence → complete` 保持统一。

数据库版本从 29 升到 30，避免旧程序将复合父节点当作可执行叶节点。升级沿用数据库备份机制；旧事件不改写，缺失 node 字段默认是独立 requirement。需要回退程序时使用升级前备份，不能让旧程序直接写入新版本数据库。

## 12. 本轮证据与适用范围

- `store::work::graph::tests`：多层研究到实现再到父验收、祖先依赖、隐式依赖环、原子回滚、过期版本拒绝、证据失效、取消分支不算覆盖、旧版本升级与重新打开数据库。
- `work::recursive_tests`：模型工具的真实临时项目流水线；证据引用缺失及关闭前文件被移除的反例；独立分支选择、全阻塞、契约/证据进展与检查点噪声的区分。
- `tests/integration/recursive_work.rs`：每步启动独立 CLI 进程，验证跨进程恢复、原子拆分、依赖选择、解释修订、父级收口以及仍需 Outcome 验收。
- `scripts/tests/browser-contracts/work-tree.mjs`：界面节点唯一、层级与依赖分离、等待原因、证据、折叠保持、键盘、宽窄布局与英文名称；随共享浏览器合同测试入口执行。浏览器数据使用 IPC 夹具，不能称为真实模型运行。
- 发布证据以最终提交上的 `scripts/verify.ps1 -Full` 回执为准。工具/CLI 测试不调用在线模型，不证明模型在任意巨大目标上能自主产出正确拆分。

当前类型提供统一生命周期和语义指导，代码不会仅凭“research”标签自动判定结论可信，也不根据行数或轮数机械判断粒度。证据引用存在及关联可由代码验证，证据是否充分仍需按验收语义检查。

## 13. 对其他模块的启发与后续边界

1. **知识与任务分离。** 项目知识记录“目前知道什么、来源是什么”，工作图记录“还缺什么、下一步产物是什么”。调研结果可以进入现有知识入口；不能把每份知识目录都实例化为任务。
2. **上下文围绕当前前沿。** 给模型当前契约、祖先目的和所需结果，完整材料按引用取回。压缩后的摘要不能替代原始验收与证据。
3. **错误形成可追溯反馈。** 回归缺陷与原目标关联，独立重现和关闭。终态工作不被重新改写成“其实没完成”，新的事实通过新节点记录。
4. **协作以契约分界。** 独立子结果可以分给不同工作线，依赖约束与所有权仍由同一个调度器维护；本轮没有增加另一套多代理管理器。
5. **进度以结果而非树大小计量。** 拆分使节点数增长是正常学习，不能将节点关闭比例作为固定工程完成率。按已验收能力、剩余关键依赖和未知报告。
6. **维护责任和有限阶段目标分开。** 本轮没有新建定时监控服务，也没有自动将所有外部反馈转为节点。现有反馈入口/日程触发后进入同一工作机制；自动导入需要独立的来源、去重和授权合同。

由此形成的架构不是无限拆任务，而是可追溯的学习—执行—验证循环：未知能变成工作，工作能产生证据，证据能更新理解，而最终关闭仍受原始目标约束。
