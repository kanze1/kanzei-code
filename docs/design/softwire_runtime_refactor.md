## 1. 产品和架构的中心

**Kanzei 承担长期工作，持续形成有依据、可接续、可使用的成果。**

对话是人参与工作的方式。模型是可切换的执行者。工具是产生作用的执行器。MD 保存可编辑的目标、约束、记忆和交接内容。工作台让人看到这些依据怎样进入行动、行动怎样形成成果，以及哪里能纠正。

核心闭环：

```text
用户目标与约束
  → 一个有边界的工作批次
  → 装配本次上下文
  → 主执行直接处理 / 委派子任务
  → 工具产生改动与证据
  → 收口、冻结版本、验证、提交或保存检查点
  → 回写成果与下一步
  → 合格经验进入记忆候选
  → 继续下一批
```

长期目标可以持续推进；一次批次必须能结束或留下真实检查点。结束一个模型 run 不结束目标；继续目标不要求保持一个无限增长的 run。

重构要统一的是执行事实、边界和反馈语义。前端图形只能展示这个闭环，不能代替它。

## 2. 已核对的问题与更深的共同原因

审计记录中的历史数量沿用该报告，没有重新统计用户数据库。本轮直接复核当前源码，确认以下路径仍然存在：

| 症状 | 当前源码证据 | 必须改变的规则 |
| --- | --- | --- |
| 写文件后不断收到无效错误 | `tools/src/local_validation.rs`：20 秒统一超时、UI 整套探针、VM 缺参数、rustfmt 缺 edition | 检查环境失败与代码失败分开；便宜检查和批次回归分开 |
| 一直编辑，没有提交尝试 | `core/src/runner/drive.rs` 周期提示只报进展；`app/src/run/events/mod.rs` 对 `max_steps == 0` 跳过收尾 | 批次交付边界独立于单次 run 的最大步数 |
| 压缩失败两次后不再主动恢复 | `runner/compaction.rs` 无效配对切点返回 0；`drive/context_budget.rs` 把它计入 futile | “切点不合法”不能消耗“摘要无收益”的同一预算 |
| 21 次并行查询为空但实际有子代理 | `app/src/collaboration.rs` 仅列其他 AppState 线路；工具描述要求每次编辑前查询 | 同级会话与子任务统一可观测，但身份与责任不同；由引擎在边界给事实 |
| 子代理只勘察，主执行承包修改 | `runner/subagent.rs::SubagentRuntime` 名册及只读快照；R-369 仍 todo | 沿现有 task 扩展隔离实现与结果整合，不再另建并行执行体系 |
| 状态观察、依据和输入分散 | `ui/index.html` 的侧栏、底栏和聊天 composer；`07-events.js::renderContextDetail` | 相同工作、请求和对象身份驱动一个常驻操作台 |

共同原因是：执行动作、可靠证据、持久进展和用户成果还没有被同一套规则串起来。错误检查反馈能不断增加活动量；活动量又掩盖缺少交付，长历史进一步妨碍判断。

## 3. 六个对象，避免继续增加一批平行概念

| 对象 | 责任 | 复用的基础 |
| --- | --- | --- |
| 项目 / 目标 | 长期意图、范围、默认偏好、验收 | 项目目录、requirements MD、配置 |
| 工作单元 | 有边界的实施结果、依赖和执行权 | Work Unit / WorkProjection |
| 执行批次 | 一个工作单元中的一次实现、整合与收口尝试 | Work events 的兼容扩展；是内部执行身份，不新增一份用户任务清单 |
| Agent Run / Task | 谁执行、归谁负责、在哪里写、如何回传 | runner、task、现有 process/session 身份 |
| 上下文与证据引用 | 这次请求确实拿到了哪些版本和片段 | Context Capsule、recall_events、工具产物、请求级 manifest |
| 交付记录 | 版本、验证结果、可用入口、决定和后续事项 | checkpoint、verification、Git 与工作事件 |

对话是上述对象的交互记录，不成为所有状态的唯一容器。相同主执行可跨多个短 run 推进同一工作；同一父工作可以拥有多个子任务。

`WorkUnitStatus` 保留现有含义。批次内部的“收口/冻结/提交待回写”等阶段单独记录，不把它们全部塞进全局 ready/active/verifying/done，也不把批次计数直接变成需求百分比。

## 4. 三种进度必须分开

1. **执行活动**：模型请求、文件修改、工具调用和心跳。说明在做事。
2. **可恢复进展**：带原始依据、版本/补丁、真实验证状态和下一步的检查点。说明停机后能接着做。
3. **已交付成果**：绑定版本、通过所需验证、具有可用入口的结果。说明产出了什么。用户认可与发布状态另外记录。

停滞监测同时读取后三者的时间和版本。文件持续变化可以更新活动时间，不能重置“距离上次可恢复进展/交付多久”的计时器。Git 提交数也不是最终成果指标：无效碎片提交不能过关。

界面优先展示当前批次、阶段、最近检查点、最近可用成果和具体阻塞。大量工具调用只留在过程详情。

## 5. 有界批次：从提示词提醒升级为执行状态

```text
实施中 → 收口请求 → 冻结快照 → 验证 → 形成交付 → 回写确认 → 下一批
                        │          │
                        │          ├─ 代码失败 → 范围内修复 → 新快照
                        │          └─ 环境受阻 → 保存检查点 → 推进独立工作
                        └─ 混杂改动无法隔离 → 保存补丁与归属缺口，不记交付
```

收口触发来自：当前验收已经满足、未检查点的时间/步骤达到配置边界、改动超出本批范围、重复相同失败且没有新证据、用户要求收口。长时间外部工具本身有独立状态和超时，不在运行中粗暴切断写入。

收口请求由引擎持久记录。到达下一个完整工具组结束边界后进入 closing 阶段：不再领取无关工作或无限派出新子任务；仍可做本批必要修复、取证、整合、验证和保存。不能只注入“请尽快提交”后继续允许无边界扩展。

closing 也有有限预算，耗尽时引擎保存版本锚点、补丁/产物引用、未完成事实和已知验证结果，写 `checkpointed_incomplete` 类型的事实；工作仍未完成。不能靠强制提交混杂文件、伪造测试通过或强行关闭需求兑现收口。

提交操作只包括可归属本批的变更。开始批次先记录已有 dirty/untracked 基线；已混杂的主树不能自动 `git add -A`。可写子任务使用隔离 worktree；无法分离的改动保留并明确列出归属缺口。

冻结与交付分开：可先保存内部快照供验证；对外的交付提交在所需验证满足后产生。若允许 WIP 备份提交，明确标 WIP，不能使批次完成数增长。

Git、文件和 SQLite 不能当成一个原子事务。收口必须有幂等阶段记录：快照 ID → 验证指纹 → Git 对象/提交 → Work event 回写。崩溃后对账已发生的阶段，补写缺失事实；不重复提交、不重放工具副作用。提交成功但回写失败显示“已提交，进展待同步”。

初始边界参数由已有运行样本校准。用户界面只给“正常推进 / 尽快收口”等少数动作，不要求用户调十几个内部阈值。无论 `max_steps` 是否为 0，收口监测都执行。

## 6. 子代理与并行检查的新关系

**主执行承担交付责任；子代理承担有边界的任务；其他会话是独立写者。**

统一活动登记至少有 `project_id, work_id, batch_id, session_id, run_id, task_id, parent_task_id?, owner, execution_mode, worktree, base_revision, scope, state, artifact_refs`。界面分清“本工作子任务”与“同项目其他会话”，不能把统一展示误写成统一所有权。

引擎在派发、开始修改、结果回传、整合、暂存/提交等边界刷新作用域、实际文件变化和仓库版本。变化时给主执行一份有界增量；空列表不反复注入，也不要求每写一行都花一次模型工具调用。仍保留手动查询用于诊断。

只检查其他会话是否正在运行是不够的：暂停/退出会话留下的未提交变更也可能冲突。共享目录使用文件版本/哈希校验和写入归属；隔离目录仍需在整合时检查基线变化和语义冲突。

继续沿 R-369：

- 勘察任务：现有只读快照与名册继续有效。
- 实现任务：`task` 的隔离能力提供 worktree，子任务只改约定范围；托管文件写与 Git 集成权继续归协调层。
- 完成任务：返回变更范围、基线、产物、验证指纹和未完成项；“子任务结束”不等于“已合并”或“父工作完成”。
- 主执行：收集结果，经现有 `merge_task` 方向整合；整合后的代码树另做所需验证，再提交与回写。
- 停止/重启：停止新派发、取消单个任务、停止父工作分别处理；R-369 首版保持“重启后不自动重新执行子任务”，只恢复身份、结果与待处理状态。重启续跑策略需另立显式契约。

不增加常驻“总指挥模型”，也不为了并行而强迫每个简单工作拆出子代理。并发由应用级资源预算管理；隐藏界面不影响任务运行，打开界面不创建任务。

## 7. 校验成为可信的证据生产服务

| 层次 | 时机 | 输出 |
| --- | --- | --- |
| 局部检查 | 文件写入后、按版本去重合并 | 快速语法/格式等有限诊断；不运行整套 UI 回归 |
| 批次验证 | 冻结本批版本后 | 对该快照的定向编译、单元/交互检查及证据 |
| 集成/发布 | 整合多任务或准备发布 | 跨模块、真实用户路径、打包和发布要求 |

校验记录包含代码快照、命令/检查定义、工作目录、工具链、平台、配置和结果。相同指纹可复用；代码或检查输入改变则过期。不能仅凭 HEAD 相同复用脏树测试。

结果统一区分 `passed / code_failed / environment_failed / timed_out / cancelled / superseded`。格式不符也应给具体分类，不宣称一定有语法错误。检查器启动失败、缺 Node 参数、Cargo 构建锁或超时都不能当成代码损坏。

D-772 首先修正确参数和阶段范围；不能只把所有超时加长。Rust edition 取目标 package/workspace 的有效值，不能在通用工具里一律硬编码本仓库的 2021。UI VM 参数与标准脚本一致。相同环境失败按条件变化后再重试，保留明确原因。

由检查配置造成的失败进入检查基础设施问题；不向项目错误经验库灌入“这段正确代码需要修复”。记忆晋升仍要匹配真实失败与恢复，校验环境改变和业务修复分开记录。

## 8. 上下文、压缩和记忆走同一份版本事实

每个 agent 每次请求有自己的上下文清单，含约束、工作、近期对话、召回记忆、工具证据、交接和折叠历史；参见 [详细设计](softwire_context_workbench.md)。父子 agent 共享明确交接内容，不继承整段历史。

D-774 的优先修复：合法工具调用/结果集合是不可分割单元，先求合法候选边界再选择预算切点。并行结果、重放消息、未完成工具与保留头尾都须校验；没有合法压缩范围就返回可解释状态，保持原文。

压缩结果至少区分 `compacted / no_eligible_range / invalid_boundary / provider_failed / no_gain`。切点无效修正算法，provider 失败做有界重试/回退；无收益才使用无收益退避。消息序列改变后重新评估资格，不能因一个 run 早期失败永久关闭该 run 的主动压缩，也不能每步重试同一个无效输入。

新的合法切点不能被压缩后的 trim-tail 又破坏；所有裁剪路径共用工具配对约束。验证失败保留原序列，不能先删除历史再发现摘要无效。

MD 内容、运行证据、索引分别保留职责：知识正文在 MD，证据账本追加保存，索引和 UI 投影可重建。已折叠原文不是已经送入模型；展示原文不是召回原文；改文件不是更改历史请求。

## 9. 操作台直接控制上述对象

工作台由四部分协同：

1. 当前需求、批次与运行状态：需求 ID/名称/状态、批次 ID/范围/阶段、执行者、正在运行或等待谁，以及最近检查点和可用版本。
2. 当前活跃路径：哪些具体版本进入哪个 agent，请了哪些工具，产生什么证据与候选。
3. 就地操作台：点击模块进入管理会话，输入绑定该模块负责人；可停靠或悬浮拖动，标题持续显示项目与接收者。
4. 工作消息：决策复核、提问、阻塞和交付反馈共用收件箱与回复操作；非模态来信不抢焦点，只有明确打开才切换回复目标。

点一个超时检查，可见“检查环境失败”及其命令，输入直接指向该对象；点“收口本批”，进入同一个批次机制；点旧记忆，可排除或重读新版并看到下次请求的实际回执。

输入属于当前工作下的具体模块/负责人会话，对象、标题、发送目标一致。草稿按项目、工作、模块、actor、conversation 与对象分开保存；回复再绑定 interaction ID 和问题版本。停靠和悬浮共用同一输入节点；后台事件不改收件人或草稿，回放不允许操作旧执行。R-371 的运行内 steer 与现有 run 边界 queue 分别表示“下一次请求”和“下一轮”，不能先改文案却仍用旧队列语义。

当前上下文、模型、工具范围与子代理状态在输入附近；设置改变按明确请求边界应用。全局设置保留默认值，任务覆盖不反向污染其他项目。

模块的管理角色按需唤起，复用现有 agent/task 身份与调度，不为每个文件额外常驻一个 agent。给已结束子任务发消息是明确续聊原任务，不能静默改发主执行。图上运行中模块缓慢呼吸，实际读写事件才出现连线脉冲；等待/暂停/完成用静止的形状和状态表达，需人判断的原因保留短文字。动画不计作工作进展。

界面优先用空间关系、连线、阶段轨道和状态图标表达结构，不重复写说明。主执行、依据、工具、子任务有不同的视觉层级。文字用于目标、对象名称、必要版本、问题和证据差异；完整来源、调用参数和设置来源在详情展开。延续现有暖白、灰绿与橙色，不通过增加颜色类别弥补信息组织。

工作消息复用事件和干预回执，明确区分待回复、已回复等待处理、已处理、失败/过期。自主决定可继续运行并供复核，提问只阻塞依赖步骤。发送回复仅入队，发起者确认问题处理且关联实际动作后才闭环；已读、关闭弹窗、模型口头回应都不替代这一证据。

## 10. 在现有代码中按责任抽边界

先在现有 crates 内拆服务，不立刻拆新仓库、新数据库或新微服务。名称为职责建议，不要求照名新建所有模块。

| 责任 | 现有接线位置 | 改造边界 |
| --- | --- | --- |
| 批次推进与收口 | `core/runner/drive.rs`、`app/run/coordinator.rs`、`app/auto_run.rs`、Work events | run 内边界监测；收口状态独立于 max_steps；外层继续只消费持久结果 |
| 上下文装配与压缩 | `runner/drive/assembly.rs`、`context_budget.rs`、`compaction.rs`、app run assembly | 一个清单、一套配对完整性规则；UI 不重算装配 |
| 任务与写者状态 | `runner/subagent.rs`、app `collaboration.rs`、process registry | 合并只读快照，不混父子与同级身份；派发/整合边界有可核查事实 |
| 验证与证据 | `tools/local_validation.rs`、`test_record`、现有 verification | 正确分类、按版本调度与缓存、分阶段检查 |
| 记忆演化 | 现有 MemoryStore / manager / recall telemetry | 复用生命周期与来源门禁，新增片段版本关联 |
| 工作台投影 | `ui/08-compose*`、`07-events`、`12-docs-pages`、`24-memory-graph*` | 共享 composer 和同一对象身份；增量渲染与回放 |

模型只决定内容与方案；程序负责可机械确定的阶段、身份、幂等、版本、计量和回执。工具说明不再替代执行契约。允许平台入口保持差异，共享核心事实；不会借本重构悄悄扩大 R-369 首版 CLI/readonly 的能力范围。

## 11. 一次大设计，分批替换

| 顺序 | 交付 | 为什么先做 | 验收重点 |
| --- | --- | --- | --- |
| P0 | D-772 校验语义与 D-774 压缩恢复 | 先停止错误反馈和长期运行退化 | 合法 async/VM 样例通过，真实坏语法仍失败；完整工具配对及失败恢复 |
| P1 | D-773 + Work Unit 批次收口 | 没有交付边界，更多 agent 只会产生更多未收口改动 | 无限步 run 内触发收口；保存失败结果；提交/回写中断可恢复 |
| P2 | 统一活动快照 + R-369 隔离实现、通知和整合 | 基于已可交付的工作再增加并发 | 两个 child 可见、独立会话脏改动可见；整合后验证；父任务不早完成 |
| P3 | 请求级上下文清单 + R-371 明确送达 | 让观察和干预有可靠事实 | 引用具体 MD 版本、分片、请求；排队/送达/已装入可区分 |
| P4 | R-381 操作台与 Softwire 活跃路径 | 以真实数据接上交互原型 | 三步内找到异常依据并纠正；更新不丢草稿；回放不改写过去 |
| P5 | 两项目长周期验证、删旧入口 | 证明闭环，再收敛冗余 | 观察真实交付与恢复，清理重复查询/提示/导航；发布另走既有流程 |

P0 两项能独立形成修复交付。P4 的 composer 靠拢可以提前做，但不得提前宣称 P2/P3 的运行能力已存在。每批都能给出具体 diff、测试和回滚点；不先把全部系统重写完再一次联调。

迁移先保留旧模式，按工作单元显式启用新运行边界。数据库采用兼容追加字段/事件版本和既有备份迁移；旧事件缺信息保持 unknown。切换旧运行器前处理新状态的兼容性，不能靠改 schema 版本号回退。读投影可逐步切换，写责任始终只有一个。

现有脏树要逐批认领/保全；新隔离 checkout 不能假装包含这棵未提交树的行为。旧设计里“全局不放聊天框”仍成立；项目操作台代替独立聊天页承载操作，Files 完整管理继续独立。

## 12. 第一条端到端验收

用一个有明确边界的阅读器开发批次：主执行装配目标与约束 → 派出只读核对与隔离实现 → 产生补丁和检查证据 → 整合 → 定向验证 → 交付版本 → 回写检查点 → 下一批。第二个项目同时推进一项无依赖工作。

在这条路上主动制造：一个检查器环境错误、一条旧记忆、一次工具配对跨切点、一个子任务失败、一次整合冲突、一次提交后回写前中断、一次用户运行内纠正。系统应明确原因、保存真实状态并继续独立工作。

记录：距最近持久检查点的最长时长、每批是否有可归属交付、重复环境失败次数、重复实施比例、压缩成功与恢复、任务整合成功、用户找到依据并纠正所需操作。提交数量和工具总数只作辅助事实。

真实观察通过前，不声称长周期自治闭环完成。这里要形成的特色是“工作连续、依据可见、交付有边界、纠正能延续”，落到同一套可验证行为上。
