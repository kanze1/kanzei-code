## 背景与问题

用户明确要求：默认进入工作台，对话降到项目内；全局管理多个项目，每个项目支持多个对话、长期维护和子代理，同时降低单项目负担、砍掉多余功能。

产品定位：**Kanzei 是让多个项目持续交付、让人集中定方向和审成果的工作台。** 对话是交代工作、纠偏与查看过程的入口；用户离开对话后，项目仍能持续推进。用户提到 GPT 和 Claude Code 是在描述期望吸收的交互特点；本文不作外部产品当前能力的事实比较。

第一性原理：人的注意力跨项目分配，目标和偏好跨对话延续，执行成本随真实工作增长。界面、数据和运行生命周期都应服从这个分工。

## 目标与非目标

1. 普通启动先回答：哪些项目在推进、正在做什么、有什么能用、哪里需要我。
2. 不进入对话，也能看懂需求、批次、机器验证和用户试用的不同状态。
3. 项目保留自己的目标、约束、工作、多个对话和长期维护记录；会话结束不结束项目。
4. 切页面不会启动、暂停、终止或重复恢复任何后台任务。
5. 单个小项目只承担完成目标所需的界面、进程和模型上下文成本。

本轮交付登记、设计和原型。正式修复、导航接线、服务拆分和功能删除按 R-381 分批进行；D-771 与 R-380 无需等待整个改版。

## 讨论摘要

- 单纯把工作台设为首页，仍留下全局“新对话”和密集工具栏，会继续让产品围着聊天组织。
- “全局管理”首先是跨项目的真实状态与明确动作，不需要常驻一个总指挥模型。
- 不把所有能力删成一个简陋聊天框：底座仍支持长期维护，但只在相关工作需要时出现。
- “负载低”同时包含认知负担、运行资源、模型上下文及维护成本，不能只折叠界面。
- 用户纠正形成返工；只有明确选择作用范围后，才写入项目或全局偏好。

## 候选方案

| 方案 | 得失 | 结论 |
| --- | --- | --- |
| 只改默认视图 | 改动小，项目、对话和全局范围仍混杂 | 只可作迁移第一步 |
| 增加常驻总控 agent 与新项目数据库 | 可以用自然语言调度，但增加模型成本、状态副本和单点等待 | 不作为基础架构 |
| 全局工作台 + 项目空间，共享事实投影，能力按需进入 | 可复用系统、逐步迁移，项目也可以很轻 | 采用 |

## 最终方案

### 1. 产品层级和默认进入

```text
Kanzei
├─ 工作台（普通启动默认）
│  ├─ 项目进展：当前工作、批次、阶段、最近实质变化
│  └─ 待我处理：待试用 / 决策复核 / 需要补充的事实
├─ 项目空间
│  ├─ 概览：目标、当前工作、最新成果
│  ├─ 工作：需求 / 缺陷及批次、依赖与验收
│  └─ 对话：本项目的多个对话，按需展开执行详情
└─ 次级入口：记忆与偏好、设置
```

全局不放“新对话”。全局主操作为“新目标”，必须选已有项目或创建项目；保存目标后可选择开始推进，保存本身不自动唤起模型。进入项目后才出现“新对话”。

侧栏在全局展示工作台、待处理和项目列表；进入项目后保留返回工作台的入口，主区域切到项目空间。对话列表只属于选中的项目，子代理只在所属工作的执行详情中展示。记忆与偏好属于次级管理入口，不与项目进展抢首屏。

启动规则：普通冷启动进工作台；明确的条目/对话/交付深链直达指定位置；从托盘恢复已有窗口保持当前页；没有项目时展示“创建项目/打开文件夹”。项目保留上次对话、滚动和草稿，返回项目可以继续；这不改变下一次普通冷启动进入工作台的规则。

开发/研究不再作为两个并列的全局宇宙：研究是项目的能力和工作类型。已有 research topic / workspace 身份先保留，通过路由适配进入项目，不能为了导航统一搬空历史课题。

### 2. 工作台应该显示什么

首屏以稳定的项目行为主，不做大量独立统计卡。顶部只显示正在推进的项目数、待我处理数和必要异常；“项目数”“运行线数”“条目数”分别计数，不混成一个数字。

每行至少回答：

| 问题 | 展示 |
| --- | --- |
| 哪个项目？ | 项目名；路径收进详情 |
| 正在做什么？ | 当前有效领取的条目标签：`R-001 · 移动阅读器 · 开发中 · P1 · 批次2/5` |
| 推进到哪里？ | 当前结果或批次名称；最多2个在途条目，其余“+N项”展开 |
| 最近有什么变化？ | 最近一次实质进展及时间；工具心跳不刷成“有进展” |
| 需要我做什么？ | 待试用、待复核、待补事实；点击进入对应对象 |

**R-380 的进度标签契约：**

- 所有 ID 都由项目范围限定，`(project_id, kind, entry_id)` 是唯一键；两个项目都可以有 R-001。
- 先按有效领取/运行关联显示正在执行的条目；历史 `doing` 只表示在途，不能伪装正在跑。运行却没有条目时显示“临时工作 / 未关联条目”，不可借用当前侧栏条目。
- 业务状态来自 tracker，批次 `done/total` 复用已有 Git 推导规则；回退使用 Markdown 时标明来源，不额外维护进度副本。
- `2/5` 明确是已完成批次，不能说开发完成40%，也不等于机器验证通过或用户认可。总量未知只显示阶段，不造百分比。
- 多线路分别显示负责人，项目汇总按条目去重；缺陷没有合理批次分母时只显示状态。
- 空闲、未关联、读取失败、状态过期分开；不可访问的项目保留旧摘要与时间，不能变成“0项/空闲”。
- 标签点击进入该项目条目详情；进入对话使用独立动作。返回保留工作台筛选和滚动。

### 3. 待我处理是统一入口

按“缺事实导致局部停住 → 可试用成果 → 重要决策复核”组织，类型可筛选。每项显示项目、相关工作、产生时间、影响及一个主动作。模型继续完成独立工作，普通未复核决定不阻塞所有项目。

复核前后的列表保持稳定：数据更新局部替换；旧项被纠正或版本变化时，已选择的旧版本要明确提示并要求重新查看，不能替用户批准刷新后新内容。用户点击完成后再收起该项，不因后台数据到达让正在阅读的行突然跳走。

**D-771 的刷新契约：**

- 按项目与决定 ID 复用 DOM；仅相关 revision 变化才更新内容。
- `observed_at` 与心跳只更新新鲜度，不参与业务内容相等判断；其他项目运行不重建当前复核页。
- 首次进入或真正新增的行允许一次入场动画；更新已有行不重播。
- 保留滚动、选择、展开、焦点、光标、中文输入法组合态和编辑草稿；请求失败保留上次可用内容。
- 编辑时可以显示“有更新”，在明确冲突校验后应用；不能无限冻结所有项目数据。

### 4. 项目空间和对话的关系

项目是长期责任边界；工作是可交付目标；对话是交代工作和修正过程的渠道；执行线路/子代理是运行资源。它们不是四份相互竞争的任务清单。

| 对象 | 保存什么 | 不承担什么 |
| --- | --- | --- |
| 项目 | 目标、约束、偏好、工作与交付索引 | 不持有永远增长的单一对话上下文 |
| 工作条目/批次 | 结果、范围、依赖、证据、决策引用 | 不复制一套聊天记录 |
| 对话 | 用户输入与可恢复会话，关联0或多个工作 | 对话“本轮结束”不裁定整个项目完成 |
| 执行线路/子代理 | 所属工作、状态、预算、产物和控制权 | 不自动成为全局独立项目或顶层聊天 |

项目默认页为概览，最多提供一个主要动作“继续当前工作”；工作列表和对话页按需进入。已有会话多线/历史恢复复用原身份；不因迁移导航创建空会话，也不复制 transcript。

单项目默认一条主要执行线；高级并行入口收在工作详情。子代理保留显式开关及“关闭 / 可用 / 运行N个 / 收尾中”状态，位置沿用项目/工作控制区。显示全局默认、项目覆盖及当前实际生效值，不能只画一个绿灯。关闭只阻止新派发；已运行子代理继续收尾，另设明确的停止动作。已有实现语义要先核对，不能本轮原型即视为接线完成。

长期维护复用 backlog、检查点、上下文归档、验证队列和偏好；普通项目无需配置角色、研究流程、知识图谱和远端服务器才能开始。

### 5. 单项目减负

| 负担 | 默认处理 | 可核查的要求 |
| --- | --- | --- |
| 首屏认知 | 全局只展示项目/待处理；项目只展示概览/工作/对话 | 不出现跨项目全局聊天列表或几十个同级工具 |
| 空闲运行资源 | 空闲项目只保留摘要；不实例化模型、会话恢复器或重图谱 | 看一次工作台不新增 session/work/decision 事件或模型请求 |
| 活跃运行资源 | 恢复、验证监视和执行仍由运行服务拥有；应用级调度共享并发预算 | 离开项目继续运行；重复进入不注册第二份监视器 |
| 前端 | 图谱、画像、研究面板按需加载；不可见页面停止渲染循环 | 隐藏图谱后无动画帧循环，切项目释放重视图资源 |
| 模型上下文 | 只注入当前项目、当前工作和适用偏好；换条目沿用已发布的上下文归档 | 其他项目数量增加不增加当前请求的项目上下文 |
| 维护流程 | 普通任务只带有界目标和必要验证；成果、决策自动收集 | 不要求模型为同一批次重复维护多份进度和验收台账 |

工作台只消费摘要投影，不直接加载全部对话轨迹、决策正文和完整需求归档。详情按需取。第一版摘要建议每项目最多2条在途工作、1条最近实质进展与计数；窗口隐藏停止轮询，活跃页以事件失效通知+合并更新为主，轮询兜底。

并发预算建议先沿用当前有效值；如首次配置，原型展示“全局最多2个活跃项目、每项目1条主线、子代理显式开启”，它是待阅读器实验校准的建议，不在迁移时静默覆盖用户既有设置。空闲项目不预分配并发槽。

### 6. 保留、下沉、合并与删除

| 能力/入口 | 处理 | 原因与后续归属 |
| --- | --- | --- |
| 多项目进展、待处理、成果入口 | 保留并提升 | 产品主要价值 |
| 自主推进、控制权、子代理开关 | 保留，明确项目/工作作用域 | 直接影响长期执行质量 |
| 对话、会话历史 | 下沉项目 | 仍方便交代和纠偏；全局不列所有对话 |
| 需求/缺陷 | 合并成项目“工作”，保留类型筛选和原ID | 同一处管理业务结果和问题 |
| 独立 Work Unit 页面/批次重复入口 | 不再新增；统一到工作详情 | 承接 R-358 的收敛方向，底层事件迁移仍由该条目负责 |
| 多线、worktree、子代理轨迹 | 下沉工作的执行详情 | 默认不让用户理解调度拓扑 |
| 文件、差异、预览、终端 | 作为项目工具抽屉和成果入口 | 使用时打开，不占据全局导航 |
| 研究、实验、SSH | 项目能力，按需启用 | 保留 R-344 等专业链路及历史课题 |
| 记忆图谱、架构、运行画像 | 次级检查工具 | 不为查看项目进度持续加载 |
| 语音、角色、手机控制 | 可选入口，默认不常驻 | 保留有效调用；不因低频直接删掉能力 |
| 重复状态条、纯工具心跳摘要、重复全局聊天入口 | 迁移后删除 | 不产生新的决策价值 |
| 无调用旧模块、被替代设计 | 完成调用审计后退役 | 列明UI/IPC/CLI/工具/测试调用者及数据归属，无迁移不能直接删 |

新增功能需说明用户、调用方、服务方和结果，且落到已有层级；没有独立用户动作或证据需求的，不新增一级页面。清理后的文档标为 superseded/historical，保留历史引用，不让旧规则继续注入模型。

## 技术选型与取舍

沿用 Rust/Tauri、现有原生 JS、tracker 与 core store；原型为 HTML/CSS/JS，不引入前端框架或新的后台服务。

拟增加独立 `AppRoute`：全局 workbench/inbox、project overview/work/conversations/detail。`last_project_route` 与全局启动页分别保存，不能继续用 `currentProject + active_space.view` 同时表达全局和项目状态。URL/通知深链带完整归属，事件处理始终按 project/process/session/run 校验。

工作台采用可重建的 `ProjectSummary` 读模型：项目身份、在途条目摘要、运行线数、验证/试用/复核计数、实质进展、content_revision、observed_at 和 fresh/stale/unavailable。摘要是派生缓存，不是工作状态的新真源；可由事件失效或目录变更后重算。业务版本与观测时间分开，前端才能稳定更新。

## 实施边界与调用方

| 改造 | 调用方 | 复用服务/入口 | 改变 |
| --- | --- | --- | --- |
| 全局路由/启动 | App初始化、导航、通知深链 | `03-shell.js`、`03-workspaces.js`、`09-sessions.js` | 导航不再等于切换/装配对话 |
| 项目条目摘要 | 工作台、侧栏、工作页 | `docs.rs`、tracker、git_batches、领取/运行事实 | 抽共享投影，不在前端再算一遍 |
| 轻量工作台查询 | 工作台 | `projects.rs::workspace_snapshot` | 返回有界摘要；不调用 create_session 或恢复流程 |
| 生命周期恢复 | App启动与已存在的运行管理器 | processes、verification_monitor、verification::recover | 从查询迁出，保持幂等及崩溃恢复 |
| 稳定复核视图 | 工作台待处理 | `12-decision-console.js`、decision_review | keyed更新、草稿保留、revision校验 |
| 项目对话/执行详情 | 项目空间 | 当前process/session路由与子代理控制 | 原ID、草稿与运行状态保留 |
| 反馈与偏好 | 用户 | 现有decision review与memory服务 | 当前选择和明确范围仍是写入依据 |

查询不再承担恢复后，需要验证应用启动、恢复失败重试与用户显式恢复入口；不能把状态悬挂当成“只读化成功”。

### 迁移与回退

先增加路由适配和摘要查询，保留旧命令与对象ID；迁移已有项目视图偏好时保留旧值；新写入只使用一套新路由，旧值只用于回退。未选择项目时不依赖 currentProject。不能通过前端轮流 switchProject 来取得全局信息。

旧入口隐藏后确认真实路径可达，再删除重复渲染与事件订阅。保留尚有调用方的 CLI/IPC；涉及历史事件/Work Unit 的迁移由既有条目单独负责，不在UI改版里顺手清库。回退可恢复旧导航，运行状态、会话、决定与成果事实不丢失。

## 验证证据

本轮：已静态核查上述入口，并登记 D-771、R-380、R-381；原型验证记录见 [README](../prototypes/workbench/README.md)。原型只证明信息组织和可点击路径，不证明正式服务性能。

实施时用 Markdown 手机阅读器为主实验项目，另一个独立项目作对照：

1. 阅读器推进 R-001，另一个项目也有 R-001，进度和对话不得串项目。
2. 阅读器缺真机OCR，只挂起对应工作；第二项目继续，工作台可见明确缺口。
3. 一个批次完成后上下文归档；返回旧对话可追溯原始事实，首页只显示新工作。
4. 决策复核录入中文时后台持续更新；草稿、光标、选择与滚动不丢。
5. 用户修改并选“本项目”，返工回原线；第二项目不得收到该偏好。
6. 子代理关闭后不再派新任务；在途状态和停止动作清楚；切到全局不终止它们。
7. 两项目运行期间重启App，恢复恰好一次；工作台不重复创建会话或worker。

资源对照统一数据和机器，分别记录1/10个已登记空闲项目、2个活跃项目时的摘要响应p50/p95、IPC字节、主线程长任务、RSS、后台活动及模型请求数。硬约束：仅查看空闲工作台新增模型请求=0，新增会话/工作事实=0，图谱隐藏后持续帧循环=0。建议10项目下摘要p95不高于500ms、切路由不产生超过50ms主线程长任务；这些为待测目标，未达成时据基线调优，不宣称本轮通过。
