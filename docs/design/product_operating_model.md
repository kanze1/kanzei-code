## 背景与问题

用户提出五件相互关联的事：验收拖慢开发；需要多项目单页控制台；记忆图谱缺少美感和动态；旧设计与功能职责不清；自动模式应先自主决定，批量交付后由用户纠正，并沉淀偏好。

第一性原理：用户购买的是持续产生、可以使用的成果。人的稀缺投入是确定目标、使用成果、纠正重要选择；机器承担实现、验证、记录与调度。产品应围绕这些责任组织，而不是让用户跟着会话、工具调用和文档状态来回切换。

核心链路：**给目标 → 多项目持续推进 → 形成可用成果与决策摘要 → 用户批量试用 / 纠正 → 修正实现与偏好 → 下一次少做错。**

## 目标与非目标

1. 用户不回答普通实现选择时，自动模式仍能完成已授权的工作。
2. 一个项目待验收、一个单元缺设备，不阻塞其他有条件继续的工作。
3. 从一页知道：谁在推进什么、什么能用了、卡在哪里、模型替我做了哪些选择。
4. 每项功能明确最终使用者、程序调用方、服务提供方、输出和失败归属。
5. 纠正一次选择后，能追到实现修改、偏好版本及后续实际采用。

最初交付为设计与原型；用户确认后已开始接入现有系统。示例数据不替代真实运行验收。

## 讨论摘要

- “验收”包含机器验证、用户试用、发布检查，三者的操作者、时机和对象不同。
- 一个问题可能是选择题，也可能是缺少客观事实。自主选择可以解决前者；设备、账号、真实路径等缺失事实不能靠猜测补齐。
- 记录模型做过的选择很有价值，但模型自己的选择不能直接变成用户偏好。
- 图谱的默认中心应是用户关心的决策、偏好和成果；代码架构关系保留为深入查看的视角。

## 候选方案

| 方案 | 收益 | 问题 | 结论 |
| --- | --- | --- | --- |
| 只放松验收与提问门禁 | 修改少 | 无法知道选择是否正确，容易把未验证当完成 | 不采用 |
| 增加独立总控 agent 管所有项目 | 可以统一解释 | 多一轮模型调用和状态副本，形成新的排队入口 | 暂不采用；先由确定性服务聚合真实状态 |
| 复用 Work Unit、事件、记忆和现有总览，补上成果 / 决策 / 反馈链路 | 改动可分批交付，旧数据可保留 | 需要理清执行、验证和用户审阅的契约 | 采用 |

## 最终方案

### 1. 验收退出开发的串行主链

每个成果显示三项独立状态，避免一个“完成”吞掉所有含义：

| 维度 | 状态示例 | 责任方 |
| --- | --- | --- |
| 实现 | 待做 / 实现中 / 已形成版本 / 返工中 | 执行 agent + 调度器 |
| 机器验证 | 未验证 / 排队 / 运行 / 通过 / 失败 / 环境受阻 / 已过期 | 验证服务 |
| 用户试用 | 待试用 / 已认可 / 要调整 | 用户 |

执行 agent 在形成可验证版本后释放写入占用，验证针对冻结的代码快照运行。无依赖的下一单元继续；依赖者只消费满足所需验证等级的版本。环境受阻是独立状态，不能冒充通过。

工作流：

```text
实现单元 ──> 冻结版本 ──> 定向机器验证 ──> 待试用成果 ──> 用户批量认可
   │                         │                  │
   └─> 推进独立单元          └─失败→修复         └─纠正→关联返工
                                                   └─偏好反馈
```

同一源码、依赖、工具链、平台和测试定义没有变化时复用已有通过证据。复用键至少包含源树指纹（含未提交文件）、依赖锁文件、命令 / 测试集版本、相关环境配置和目标平台；不以“刚刚跑过”或单独 HEAD 判定。变更影响范围无法可靠确定时扩大验证范围。

代码编写阶段跑定向检查；集成阶段验证跨模块契约；发布阶段保留完整发布检查。多条线共享构建资源时由验证队列协调，不占着模型等待同一个构建锁。环境失败给出原因和可恢复动作，同一失败条件不自动无限重跑。

每次交付提供一个短成果包：能做什么、入口 / 产物、绑定版本、已验证与未验证路径、相关决策、已知问题。用户可以批量试用；不需要读测试日志才能知道如何使用。通过机器验证不自动等同于用户验收或发布。

允许未审阅成果积累，但在项目上配置波次容量，避免无限建立在未经确认的产品方向上。积压时优先做无争议的独立工作，并在总控显示待审阅数量；不弹出普通提问阻断全部项目。

例：截图中的 B3 可拆为“附件能保存并恢复”“PDF 能提取并检索”“Reader 能打开和搜索”“目标平台与真机 OCR”四个可独立证明的结果。真机 OCR 缺设备只影响对应结果；已可用的 Reader 先给用户试用。不能把任一子结果通过冒充整项 R-001 完成。

### 2. 自动模式：把提问转成可追溯的自主决定

所有问题先经过同一个问题处理服务，CLI、桌面、自动续跑和子任务共用策略，避免某条入口继续弹窗。自主决策与权限策略是两个维度，已有授权直接消费，不再重复索要。

| 问题类型 | 自动模式动作 | 用户何时看到 |
| --- | --- | --- |
| 普通实现 / 产品取舍，有已授权的可执行方案 | 查当前指令和适用偏好 → 模型选方案 → 持久记录 → 返回明确的 agent decision → 继续 | 波次决策清单 |
| 选项有分歧但可逆、成本在现有预算内 | 选改动较小且容易调整的方案，记录假设与影响 | 波次清单优先展示 |
| 缺少不可推断的事实，例如真实设备或指定目录 | 记录需要的信息，只挂起依赖它的单元，调度独立工作 | 总控待处理区 |
| 涉及现有授权之外的实际动作 | 保留当前授权边界，记录具体动作与影响，先推进独立工作 | 总控待处理区；不把模型选择伪装为用户授权 |

自问自答由当前模型完成，不默认再开一个模型或辩论轮。服务返回结构化决策请求，模型提交简短选择和理由；确认记录落盘后才执行依赖该选择的动作。不采集隐藏思考过程，也不要求长篇论证。

本批在原项目库中按 `run_id + session_id + 原问题` 去重，保留 `tool_call_id` 作为调用来源；这样模型补交决定时即使换了调用 ID，也会更新同一条记录。已完成的决定不被重试覆盖。真实缺失事实有独立状态；跨运行语义去重和无效决策尝试次数上限仍需后续完善。

删除自主模式中“QUESTION_PENDING 一律停止”和“结尾像提问就停止”的决策权；停机以结构化结果为准。自然语言检测只作诊断信号。结伴模式仍允许真实交互问答。发现了真正待输入的单元，不代表项目或所有项目都必须停止；只有没有可执行工作时才进入等待。

#### 决策最小记录

| 字段组 | 内容 |
| --- | --- |
| 身份与归属 | decision_id、版本、project_id、work_unit_id、session_id、run_id、tool_call_id、波次 |
| 选择 | 问题、候选方案、选择、简短理由、待证实假设 |
| 依据 | 当前用户指令引用、适用偏好 ID / 版本、事实证据引用 |
| 影响 | 受影响成果 / 文件范围、可逆性、调整方式、依赖的决定 |
| 执行 | 已提出 / 已采用 / 执行失败 / 已被替代；产物与验证引用 |
| 审阅 | 未审阅 / 用户认可 / 用户纠正；反馈原文、范围和时间 |

执行状态和审阅状态分别保存。`actor=agent` 永远保留；系统不能返回 `User answer` 来伪装自主选择。未审阅也不代表选择没有执行。

记录保存失败时返回可恢复错误并保存原调用事件；该选择的依赖动作不伪装成“已留痕”，其他独立工作继续。用户对旧版本的批量认可必须校验版本，不能顺带认可列表刷新后新出现的决定。

### 3. 人的纠正同时改变实现和记忆

用户审阅时只有三种主要动作：

- **认可这次选择**：关闭这次待审阅项，不默认推广为所有项目的习惯。
- **修改这次选择**：形成关联返工，旧选择保留为被替代；相关验证变为过期，不能继续显示旧的通过结果。
- **修改并记住**：返工之外，明确作用范围——仅当前任务、本项目、所有项目。

全局记忆的数据分两层：所有决策可以提供候选经验；只有用户明确认可为偏好或纠正并选择相应范围的内容，才成为有效偏好。用户没有反对、某次自动测试通过，都不能算作用户同意。

适用顺序：当前明确指令 → 当前项目的已确认偏好 → 适用的全局已确认偏好 → 可参考的候选经验。范围不匹配的偏好不注入。每条偏好保留来源决定、用户反馈、适用条件、版本和被替代关系。冲突时采用更新且更具体的有效指令，并记录冲突，不悄悄覆盖原记录。

下一次模型使用偏好，要记录 `preference_applied`，绑定具体版本和新 decision_id。图谱中的“采用”边只能由这个事实产生；召回、读过、采用、改善结果是不同事件。纠正旧偏好后，对在途、确实依赖它的决定标记“需要重查”，不把所有项目全部判为失败。

### 4. 一页多项目总控

默认进入总控台。一级操作只保留四个面：**总控、成果、决策、记忆**。项目、开发 / 研究类型和当前波次作为筛选范围。对话、文件、架构和运行日志从当前任务的详情进入；设置仍有独立入口。这里是导航整合方案，不是取消研究、文件或架构能力。

总控首屏：

1. 顶部：运行项目数、待试用成果数、待审阅决定数、真正缺信息的单元数。
2. 中部：按项目排列的工作行，显示当前结果、执行 / 验证状态、最近实质变化、已有成果和决定入口。
3. 右侧：选中项目或决定的详情。可以解释选择、认可、纠正并选择记忆范围，不离开总控。
4. 下方：这一波已形成的成果；日志默认折叠，只在解释失败时出现。

需要用户输入的事项优先显示，其次是已形成的成果、未审阅的高影响决定、普通运行状态。排序稳定，状态更新不让行不断跳位。没有明确总量时不显示伪百分比；使用结果名、阶段、最后进展时间和证据。

多项目聚合使用现有 workspace_snapshot 的演进版本，由应用服务读取各项目投影。前端不切换 currentProject 来轮流读取数据；后台运行不依赖当前导航。每条事件带 project_id / session_id / run_id 和递增序号，断线重连补投影；项目不可达时显示“状态过期 + 最后更新时间”，不能推断为空闲。

只读快照与开始 / 停止 / 审阅命令分开。动作使用明确项目及单元 ID，校验记录版本，服务确认后更新；不能把本地按钮变化当作后台执行成功。

### 5. 图谱展示“为什么这样做，后来如何改变”

默认只展开当前决定附近的一到两跳：**来源 → 自主决定 → 成果 → 用户纠正 → 项目 / 全局偏好 → 后续采用**。按项目、范围、时间筛选；大图先聚合，点开再展开。现有“按代码架构看记忆”保留为第二视角。

图谱沿用已捆绑的 force-graph。库本身支持 Canvas 力导向、拖拽缩放、点击聚焦、动态数据与按需粒子，无须为了“有动画”换栈。[上游 API](https://github.com/vasturiano/force-graph)

| 备选 | 能力与取舍 | 当前决定 |
| --- | --- | --- |
| force-graph | 当前已有离线包和共享封装，支持力导向及关系动效 | 优先复用，先解决信息设计 |
| Sigma.js | WebGL 大图渲染，配合 Graphology 管理图数据 | 真实规模证明现有方案不足时再测；[官方文档](https://www.sigmajs.org/docs/) |
| Cytoscape.js | 图分析、交互与布局生态，适合更复杂的网络分析工作台 | 当前决策审阅无需增加此栈；[官方文档](https://js.cytoscape.org/) |

只做三种有意义的动画：新增关系渐入；选中决定时邻域聚焦；回放 / 实际采用时沿对应边流动。稳定后不让整张图持续漂移。隐藏页面暂停，尊重减少动态效果，提供等价列表。动画不代表“偏好有效”，只表达已记录的事件。

## 技术选型与取舍

复用现有 Rust 服务与事件存储、原生静态前端、离线图库，不增加总控 LLM、框架迁移或独立图数据库。新增高频 decision / review 事件及可重建投影，稳定偏好进入既有 Markdown 记忆。A-* 继续承载长期产品 / 技术决定，不要求每个普通实现选择写成一篇 A-* 文档。

将 Work Unit 的当前状态迁移为执行、验证、审阅三个维度，必须显式版本化。旧 done 只映射为旧规则下完成，用户审阅状态为 unknown，不能倒推出用户认可；旧 checkpoint 决策只导入历史引用，不能补造候选项、依据或全局偏好。

先在既有事件表增加兼容事件类型，再接新命令，最后切换调度；本批 SQLite schema 仍为 25。出现问题可退回旧调度和旧界面读取，新事件保留。控制台不依赖一次性改完全部后端。

## 实施边界与调用方

下表按产品能力归属；它不是已经证明所有底层工具都有调用方的全仓静态审计。

| 能力 | 最终使用者 / 触发者 | 程序调用方 | 服务提供方与输出 | 新位置 / 处理 |
