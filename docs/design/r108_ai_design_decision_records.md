## 背景与问题

项目已有需求、缺陷和决策追踪，但 AI 讨论中的问题拆解、候选方案、技术取舍和方案变更没有统一入口。只写最终结论会丢失演进依据，只保留聊天全文又难以检索、复用和判断哪些内容已经成为约束。

## 目标与非目标

目标是形成一条团队可共享的知识链：需求/缺陷说明要解决什么，设计文档说明如何讨论和实现，A-* 决策说明哪些取舍已经稳定。方案变化可追溯，验证证据可定位。

非目标是保存所有聊天原文、引入新的数据库或把设计文档变成运行时配置。本轮沿用既有 Markdown 文档、decision 工具和状态机。

## 讨论摘要

- 已有 `.kanzei/project/decisions.md` 能保存稳定结论，并由既有工具分配 ID、校验状态、引用和归档。
- `docs/design/` 已经承载多份设计基线，但缺少统一元数据、候选方案和变更记录规范。
- `.kanzei/summaries/` 是临时总结目录，不适合作为团队共享真源。
- 因此需要让设计文档保存过程，让决策条目保存稳定约束，并让两者互相引用。

## 候选方案

### 方案 A：只使用 decisions.md

优点是入口单一、状态和归档已有工具支持。缺点是长篇背景、候选比较、实施边界和验证轨迹会挤进追踪条目，难以阅读和维护。

### 方案 B：只使用设计文档

优点是适合长篇设计和演进。缺点是稳定约束没有统一 ID、状态机和上下文注入入口，后续讨论容易重复或覆盖旧结论。

### 方案 C：设计文档记录过程，决策条目记录结论（选择）

设计文档保存背景、讨论摘要、候选方案、最终方案、取舍、变更和验证；稳定约束使用 A-*，并由设计文档与决策条目双向引用。该方案保留过程证据，同时复用既有 decision 工具，不增加运行时和数据库复杂度。

## 最终方案

采用方案 C：

1. 新设计主题在 `docs/design/` 建立一个 `snake_case` Markdown 文档，并使用 `docs/design/readme.md` 的最小结构。
2. 产生长期约束时通过 `decision add` 创建 A-* 条目；讨论中的条目保持 `draft`，用户接受后才转 `accepted`。
3. 设计变化追加“变更记录”，不覆盖旧结论；旧决策被新方案取代时转为 `superseded`，明确否决时转为 `rejected`。
4. 需求/缺陷、设计文档和决策条目相互引用，验证命令和结果写入设计文档及对应追踪条目。

## 技术选型与取舍

- **存储**：沿用 Markdown 文件，避免引入新数据库；优点是可读、可编辑、可由 Git 恢复，代价是结构完整性依赖既有 tracker 和文档检查。
- **决策状态**：沿用 `draft → accepted → superseded/rejected`；优点是与现有工具一致，代价是用户接受动作不能由本轮自动假定。
- **讨论记录**：保存提炼后的摘要而非聊天全文；优点是团队检索噪声低，代价是原始上下文需要通过运行轨迹或外部来源回看。
- **命名**：新文档使用 `snake_case`；既有历史文档不做无关重命名，避免产生无意义的大批次变更。
