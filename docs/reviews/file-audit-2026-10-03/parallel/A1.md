## 可达问题与证据

**A1-01 / P1：未登记到数据库的压缩发布者与 GC 没有互斥。** 手动压缩保持数据库 idle，先写 `context-{hash}.txt`，再 await LLM，最后提交指针；app 轮末也可能已完成输入后再压缩。GC 此时判断文件无引用并实际删除，压缩成功却提交了无法读取的归档指针。

负例 `gc-before.log` 使用真实 core 压缩算法、LlmClient 和本地 HTTP SSE 服务。HTTP 屏障确保 blob 已创建、模型尚未返回，旧 C0 清理入口仍成功；测试在“GC must reject while the archive has no committed reference”断言失败，exit 101，编译已通过。补锁后同一窗口拒绝整理及会话删除；成功提交后空闲 GC 保留正文，checked commit 被 source reset 拒绝后孤儿可正常回收。

**A1-02 / P1：裁剪后的 surface 在没有耐久事务时被发布或丢失。** CLI 把 overflow_traces 非空当提交前提，纯 L0 没有该 trace；app 轮末仅设置 LLM compaction 事务，纯 L0 只改缓存；app 轮内 L0 的 RunSummary 也可能已经低于预算，轮末完全不再压缩。另有 app L0 先改缓存再 await LLM，取消会留下未提交指针。结果是缓存与恢复不一致，输入结束后 GC 还能删掉缓存中的原文。

负例 `prune-before.log` 通过真实 prune→CLI 收尾 surface 函数→recover_cli_prior 发现恢复仍为未裁剪原文，exit 101，编译已通过。修复后按本轮来源与结果的实际差异提交，普通 typed 轮次不追加重复事务。app 在 typed finish 后、idle/finish_input 前提交轮内替换；轮末保持结果局部，commit 成功才更新缓存。写失败或取消继续使用已提交版本。

**A1-03 / P1：旧来源的轮末压缩与缓存发布会覆盖后到事实。** 既有 app 轮末 compaction 事务没有来源 CAS；等待模型期间 mobile 可独立提交 UserMessageCommitted，随后旧 surface 替换会盖住新消息。手动/轮末提交后再单独取缓存锁的窗口也可覆盖先到的缓存 append。

修复保留本轮来源 receipt，并在事务内 CAS；source 不匹配时保留当前 durable/cache。app 从最终来源读取到 CAS/cache.insert 持同一缓存锁，finalize 初次 durable→cache 同样在锁内完成，所有 await 留在锁外。实际 typed writer + mobile UserMessageCommitted fixture 证明普通轮不制造 compaction，stale 候选不覆盖手机消息；两连接回归证明 sequence capture→projection 期间的新事件使 run CAS 拒绝，活动输入本身不会误拒绝。实施中曾否决 `current != summary` 就提交的扩大规则；该候选没有交付，不把它列成旧仓缺陷。

流水线 receipt 含内部 fixup 用户提示，而 durable typed 流水线没有同一条用户事实。测试验证此时不发布无法证明来源的压缩候选、保持已提交历史；**没有证明这种 mismatch 流水线的压缩 surface 被成功发布**。取消或拒绝后未发布的归档可由 GC 收回，缓存不留下悬空指针。mobile 自身 cache→DB 发布顺序由主代理 M2 单独修复，本包不扩写 mobile.rs。
