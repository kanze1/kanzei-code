## crates/kanzei-base/src/write_log/codec.rs

### 职责
全文审查：在持久化边界编码和校验日志正文、路径、归因身份及旧格式。

### 判断
P2

### 确切问题
- 源码写工具接受 Unix 合法的含 CR/LF 文件名，`record_worktree_write_log` 不拒绝这类路径，直接传给 WriteLogEntry。codec 把路径裸拼进六行；`record` 可以返回成功，随后 `entries_after` 和任何新 `record` 都因该日志行数错误失败。路径末尾 CR 还会被 `str::lines` 作为 CRLF 的一部分剥掉，造成身份改变。
- 条件较窄；读取失败已有显式错误兜底，但会使整本日志后续记录和围栏归因不可用。不是以缺少测试或猜测平台差异定级。

### 修改
- 仅在 path/run_id/process_id 含 CR/LF 时使用显式 `v3:<at_ms>` 首行，并将这三个 UTF-8 元数据字段 hex 编码，仍为六行；正文三态和指纹校验不变。
- 普通元数据继续写原六行格式。读取同时接受旧格式和 v3；未知版本、非法 hex、非 UTF-8 显式返回 InvalidData。
- 共享现有 hex 原语用于正文及元数据，未增加依赖。主代理已在修改前确认 caller 清单与持久化兼容边界。

### 影响范围
- 全部日志构造与 managed/cross_tree 读者，无 public API 或 caller 修改。
- 旧日志保持原样，普通新日志格式不变。旧二进制不识别 v3 记录；本轮仅本地提交，没有发布或操作用户日志。

### 验证
- 修复前真实 `record → entries_after` 回归退出 101，已复现“记录成功后无法读取”，不是仅测试私有 codec。
- 修复后 LF、末尾 CR、CRLF、中文正文和归因身份完整回读；随后普通写入仍成功，普通记录保持原首行与路径。
- 恶意/损坏版本、奇数 hex、非 hex 和非 UTF-8 经真实读取和追加均失败，原日志不变且没有追加新日志。
