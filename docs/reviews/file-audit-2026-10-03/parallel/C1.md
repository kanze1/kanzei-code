## crates/kanzei-core/src/store/processes.rs

### 职责
持久化线路登记/设置及永久退役身份，提供读取、创建、更新和注销；全文审查。

### 判断
P1

### 确切问题
- app process_update 取出 handle 后释放进程表锁，再经 persist_process 落库；另一操作可先注销并写入 retired_processes。旧 upsert 随后无条件插入已删除行，让退役与活动登记同时存在，刷新/重启后复活关闭线路。
- insert_new_process 只判断活动表，旧分配结果在另一连接创建并注销同身份后仍能复用退役 ID，继承历史会话和持久设置。与前项是同一退役写入门禁根因。
- 此前竞态已经留下的 live/retired 双表重叠会被 list/get 当活动记录恢复，不能仅阻止未来写入而继续暴露旧错误状态。
- 既有 list 按 v25 规则返回 simplify ID，但库仍可能只有旧 verbatim 行。delete/get 只按 exact ID，合法注销可零行成功且不登记退役，重启继续恢复该线路；单条查询也会错误报告不存在。已有两别名行时注销只删一行，另一行继续存在。这是独立的读写身份合同问题。

### 修改
- upsert 和 insert_new 都在单条 INSERT SELECT 中检查 retired_processes，检查与写入由 SQLite 同一 statement 序列化；不增加先读后写窗口。
- 退役 upsert 返回已有 InvalidInput 错误；insert_new 沿用冲突返回 false 的契约，活动行不受改写。私有 process_id_forms 完全委托既有 path_forms，所有门禁匹配同一实体的原始/simplify/verbatim 三形态。
- list 用 SQL 排除 exact 退役行，再按已有 simplify_process_id 归一后的退役集合排除跨别名重叠；get 的同条 SQL 同时匹配三形态活动/退役行，选最新活动记录并复用 list 的归一 owner。退役账本优先，保留历史及旧行，不加启动迁移或新 schema。
- delete 在同一既有 Immediate 事务中按全部 forms 登记/删除；新退役身份用 simplify 形态和最新活动行的实际 owner，已有任一形态的退役记录保持原 owner/时间，不重复创造注销时间。

### 影响范围
- 直接写入 caller：app/processes/registry.rs 的 persist_process/register_process，注销由 lifecycle.rs 和 registry.rs 的失效工作树清理调用。
- app 默认线路设置、并行线路设置、恢复及历史关闭列表；合法新 ID/现存活动行更新不变，退役身份写回被拒绝，旧别名不再造成注销/单条查询失败。字段、库版本和 API 签名兼容，路径规则不变。

### 验证
- `retired_process_rejects_late_snapshot_and_identity_reuse`：两个独立连接模拟旧设置快照 → 同伴注销提交 → 旧更新晚写；确认 upsert 报错、insert false、活动行不存在、退役账本保留、新身份正常创建、重开仍不复活。
- `retired_ledger_hides_live_rows_left_by_old_race_after_reopen`：旧双表重叠 fixture 重开后 list/get 均不暴露退役 ID，普通活动 ID 保持；只读连接行为一致，upsert 拒绝/insert false，历史及物理旧行不被删除。
- `retirement_guards_share_existing_verbatim_identity_rules`：live/retired 的带前缀与无前缀两方向重叠，全部读写门禁识别同一身份；注销删除旧活动别名，原退役时间 123 保持。
- `deleting_returned_id_retires_all_verbatim_aliases`：只有 verbatim 行、同时有较旧 simplify 行两个场景，list 返回合法 ID 后 get 选同一最新记录，注销登记退役并删除所有活动形态，旧快照不再写回。
- `cargo test -p kanzei-core store::processes::tests -- --nocapture`：14 passed / 0 failed；合法活动更新、首次建线、冲突不覆盖、模型/开关往返、旧库升级和退役历史排序均通过。

## crates/kanzei-core/src/store/notifications.rs

### 职责
保存线程通知、原子分配序号、按序回放，并持久化设备/线程投递游标；全文审查。

### 判断
P1

### 确切问题
- 同一设备/线程允许 GET 和 SSE 或多条连接同时投递。旧批次若最后完成，其较小序号会覆盖已保存的大游标，重连后重复补发已投递事件；旧 UPSERT 无条件覆盖造成可达 lost update。

### 修改
- 单条 UPSERT 用 MAX(existing, incoming) 推进持久游标，让多 writer 晚到旧提交不能倒退。
- 不修改显式请求 cursor、线程内通知序号分配、event_id 幂等语义和设备键口径。

### 影响范围
- app/mobile.rs GET /v1/notifications 与 mobile/sse.rs 投递提交；所有生产 setter 只推进，没有重置 caller。
- 状态库 device_id/thread_id 联合键隔离及重连回放；API、存储格式兼容。

### 验证
- `delivery_cursor_does_not_regress_when_old_batch_commits_last`：两连接取不同长度批次，新批次先提交、旧批次后提交并尝试 0；保持最大 3，设备/线程隔离，重开后仅回放 4，显式 cursor=0 仍回放全部历史。
- `cargo test -p kanzei-core store::notifications::tests -- --nocapture`：4 passed / 0 failed，包含 4 worker ×20 通知序号连续/不丢失、序号冲突拒绝及回放。
- core 全包及 all-targets Clippy 通过；MAX 更新在同条 SQL 内完成，没有读后写窗口。
