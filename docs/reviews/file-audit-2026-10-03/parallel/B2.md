## 依赖与状态地图

`base 文件锁 / harness pending_question + AsyncMailbox → core SubagentRuntime / project_state_path → tools TeamStore → AgentTeam registry / lifecycle / worker → app agent_team / run coordinator / stop / UI`。

- `TeamStore` 的 SQLite JSON 记录是任务、消息、revision 和 transcript 的持久真源，`update` 已使用 Immediate 事务完成读取、修改和提交。
- `TEAMS` 是进程内 `(物理项目根, owner)` 对应运行 owner 的唯一注册表。根身份沿用既有 `worktree_key`，没有新增 normalization。
- `AgentTeam.lifecycle` 拥有准入、取消 token、结束清理和采纳的串行边界；`active` 保存每个原 worker 的 `Arc<CancellationToken>` 身份；attempt 来自持久任务记录。
- 所有 queued→launch 都在同一 lifecycle 内：spawn 的 insert/emit/launch、queue_message_locked 的更新/launch、finish 的清理/交接；wait 在该锁内读取持久记录和原 token 快照。没有执行者的持久 active 状态不表示任务仍在运行。
- 提问 router 的同步 prefix 负责 save/register，返回的 future 只负责等待；提问文件状态由 harness 拥有，app 的 actor 代数和最后 cancel_owner 收口由 A2/主代理负责。

锁序：注册锁内只执行无回调的同步 SQL/Inner 构造，不获取 team/app lifecycle，不跨 await。已有 owner 的 runtime/config/mailbox 刷新在释放注册锁后。worker/消息/stop/ask prefix/finish 为 `team.lifecycle → active / TeamStore / question 文件锁`，事件与主邮箱可继续进入 `app.lifecycle`，没有 app→team 反向调用。SQL 事务提交后才 emit。reply、LLM、接收器、permit 等待及后台进程清理不持 lifecycle。app adopt 先 await writer lease，再进入同步 team adopt，锁序是 `writer lease → team.lifecycle → Git / TeamStore`。

已搜索全部 attach/find/TeamStore::open/set_ask_router 及 active/state 写者。app/run/coordinator 与 app/agent_team 是 attach caller；commands/run、processes/lifecycle、collaboration、runtime_service、side_question 使用 find。side_question 的 orphan 分支只改内存投影，没有恢复写入。active 仅由 launch 和 finish 写入；tools/team/tools 的 inbox 只处理消息，不改 worker state。没有持久化格式、文件布局、Tauri command 或 UI 事件变更。

## crates/kanzei-tools/src/team/mod.rs

### 职责
拥有同一对话的团队注册、恢复、消息准入、worker/token、提问和停止/采纳状态机。

### 判断
P1

### 确切问题
- 并发 attach 分别 find(None) 后各自恢复/创建，最后注册覆盖第一份 owner；停止查 registry 只能看到其中一份 active。
- list/get 使用旧的 absent 观察直接恢复数据库，与 attach/启动交错可把 live job 写成 interrupted。
- child router 同步保存问题没有 stop 准入边界，停止枚举结束后仍能新增 pending；迟到 reply 状态恢复也能覆盖 stopping。旧 job 快照的 attempt 还没有包含本轮递增值。
- worker 已返回 Ok、outer 尚未删除 active 时 stop 写 stopping；旧 cleanup 跳过错误分支，移除 token 后留下永久 stopping。Err 收尾会把已受理的新 queued 跟进写回 failed；模型超时/失败被 core 转为失败 ToolOutput 后，worker 又是 Ok，同样会丢失已受理跟进。
- adopt 检查 done 后 apply/commit 未与消息准入串行，明确 resume 可启动新 attempt，而旧 adopt 随后写 adopted 覆盖正在执行的任务语义。
- lifecycle 的持久失败处理不完整：launch 在 active 注册后写 queued 失败留下从未 spawn 的 phantom worker；final state 保存失败移除 worker 后，wait 仍按旧 running/queued 永久等待；stop 在 SQL 更新、问题清理或记录读取失败时不取消真实 worker，bulk stop 还静默吞错。取消后的最终状态保存失败也可能按旧 queued 重新启动已停止队列。

### 修改
- get_or_register 在单一注册临界区完成查找、恢复、创建、插入；统一 recover_interrupted。新增 store_for_inspection 重新核对当前 owner，活跃 owner 返回其原 store。
- active 使用原 Arc token 身份。worker 状态转换、ask 同步 prefix、原 token/attempt 校验与 stop 共享 lifecycle；等待在锁外。ask 捕获实际递增后的 attempt；child mailbox 创建也在原 worker 准入边界内。
- finish_worker 在同一 lifecycle 内校验身份、收口 cancel/错误、移除原 active 并交接已经排队的明确续做；cancel 后后台进程清理在锁外等待，Ok 也不能跳过已经发生的 stop。launch 保留原准入消息 ID 的私有快照，Err 和 failed ToolOutput 仅交接后来新增且仍 queued 的跟进；只有原始 queued 消息时保留 failed，避免自动重放形成错误循环。stopping 期间 resume 明确报错；停止完成后显式 resume 仍合法。
- adopt 的 done 检查、实际 Git apply、adopted 提交同步串行化；launch 写 queued 失败时回收刚注册 token 并通知等待者。
- wait 读取 jobs/token 的同锁快照，无执行者时明确报错并保留事实；spawn 的 insert/emit/launch 合并到同一私有准入边界，防止正常启动被误拒。stop 尽力取消原 token、关闭邮箱，SQL/问题错误仍返回或记录；bulk stop 即使无法读取该 ID 的记录也取消已持有的原 token。取消后的 finish 永不自动交接队列，故障解除后显式 stop/resume 正常。

### 影响范围
- app 两个 attach caller、list/get 恢复、全部 stop caller，以及 core DelegationHost；TeamAsk 同步 prefix 的内部锁契约与 app 配合。

## 跨进程入口核对

main.rs 的 `--runtime-service` 在 main 线程持 `service_lock()` 的 OS FileLock 至退出；普通桌面非 local command 经 `runtime_service::route` 转发此唯一服务。相同程序/home 的两个普通窗口不会产生两个 Team owner，因此撤回初步的“默认两窗口跨进程假恢复”判断，不记为 P1。`KANZEI_EMBEDDED_RUNTIME` 是测试使用路径，不能单凭该 flag 记产品 bug；CLI 没有 AgentTeam::attach caller。

继续核对的真实入口是受支持的不同 portable exe/profile：runtime_service::directory 明确按 exe hash + kanzei_home 分离服务，TeamStore 的 project_state_path 却固定为真实项目 root/.kanzei/state.db，默认 session owner 也只按项目根计算。源码已经确认这些身份边界，尚未执行两个隔离 runtime 打开同一临时项目的原生回归；不据未执行的路径计 bug，不引入新跨进程租约。主代理后续先做该实际入口验证。
