## 执行与验证

1. 大块按用户优先级；每块内部按状态/存储 → 执行逻辑 → API → UI 的实际依赖顺序。选中界面块不代表先改 UI 再补下层合同。
2. 每包先确定文件所有权、状态 owner、调用方、持久化和并发边界；public API、序列化、schema、路径/锁/hash 语义修改前搜索全部 caller。
3. 只认定可达的 correctness、状态一致性、并发、依赖和失败语义问题。无实际问题写 PASS，不为风格修改；先完成剩余范围审计与根因归并，再进入修复阶段。
4. 有并发或持久化修复时提供直接证明 bug 的回归或故障注入；实际修改执行相关 check/test、caller 和失败路径验证。纯计划变更只检查文档、JSON、引用与差异。
5. 逐文件记录继续使用职责、判断、确切问题、修改、影响范围、验证六节；包末保留 Module Summary 五项。切片、候选、编译通过不得冒充全文审查。
6. 复用现有工作树；一个文件一个写入者，共享 Cargo target 由主代理串行协调。并行工作只能在当前四块范围和已明确文件包内进行。
7. 每轮更新实际修复、验证和本范围进度。历史 coverage 不重置，移出范围不算 PASS 或完成；不以旧报告中的下一步扩大本计划。
