**核心判断：现有全局、项目、模块、详情的层级可以保留。主要问题在于页面职责、控件作用范围和视觉重要性没有对应起来。** 对话输入框承担了页面导航、项目上下文、对话配置、连续运行、权限和应用运行状态；项目管理被叫作“概览”；需求列表混入了对话标题；文档同时保留数代产品定义。只改间距、圆角或颜色，不能解决这些问题。

**2026-10-04 用户补充的优先约束：通用设计直接复用熟悉的 Codex 和 Claude Code 交互，特色功能才按自身需要扩展。** 本文已经据此修订，不再把重新分组、移动控件或减少按钮数量本身当作设计目标。这与项目既有 `docs/design/direction_taste.md` 的复刻优先原则一致；该文件中的历史功能对照表不作为外部产品当前能力的证据。

具体边界：

- 桌面布局与日常操作优先选择用户熟悉的 Codex 作为整体参照；工具过程、执行反馈等再吸收 Claude Code 的习惯。一个完整操作流程使用一套一致规则，避免每个控件分别抄一种产品。
- 通用交互包括对话导航、输入、附件、模型、思考强度、模式、权限、发送、停止、快捷键、工具展开和文件差异。优先沿用已有的位置、顺序、动作含义与反馈，再去除 Kanzei 后加的重复信息。
- Kanzei 的多项目长期推进、需求/缺陷与执行关联、批次交付、记忆管理与追溯等需要补充自己的信息结构；其中已有成熟通用做法的部分仍优先复用，不把整个管理页都当成自由创新区。
- 不因作用范围不同就机械移动控件。应用级权限仍可在输入附近提供熟悉的快捷入口，同时准确显示生效范围；作用范围清楚与入口靠近输入并不冲突。
- 普通交互要偏离参照时，先写清参照行为、Kanzei 的特殊需求以及复用为什么不足。正式布局对照用户实际使用的版本核验，不凭记忆给 Codex 或 Claude Code 下当前行为定义。

**一、先明确每个区域只需要回答什么**

| 区域 | 用户需要得到的答案 | 应保留的主要内容 |
| --- | --- | --- |
| 全局工作台 | 哪些项目在推进，哪里需要我 | 项目摘要、跨项目待处理、进入项目 |
| 项目管理 | 这个项目有哪些工作，进展和交付如何 | 需求/缺陷、当前工作、交付、必要的运行与资源入口 |
| 对话 | 我正在和谁协作，说了什么，下一条发给谁 | 对话正文、必要的过程摘要、明确的接收者和输入 |
| 工作详情 | 这个需求具体要完成什么，还有什么没完成 | 目标、验收、批次、证据、负责对话的链接 |
| 运行详情 | 当前执行在做什么，为什么等待，怎样控制 | 阶段、工具、子代理、连续运行策略、停止动作 |
| 设置 | 默认行为是什么，影响多大范围 | 应用偏好、项目覆盖、对话覆盖及生效时间 |

这些是职责划分，不要求新增六个一级页面。现有页面、右侧面板和菜单足以承载。重点是同一个对象在不同位置有不同深度的投影，而不是到处完整复制。

**二、输入框过载：必须先分清作用范围，再减少常驻控件**

截图中输入区已有约十五项可点击操作，外加项目、分支、改动量、生成状态和子代理状态。上方切页、中间写消息、下方配置与控制，用户发送一句话前需要扫过多种含义。

源码进一步确认：

- `26-project-conversations.js:284–300` 把“对话 / 概览”、运行信号、需求开关直接 prepend 到 `#composer`。导航与输入框的绑定是结构性的。
- `index.html:225–248` 的项目上下文带同时放了分支、改动与子代理开关。
- `index.html:275–385` 的工具行包含模式、鞭挞、自动放行、模型、思考、旁路提问、后台常驻、更多、排队、语音、停止和发送。
- `03-layout.js:116–129`、`07-events.js:1024–1047` 显示自动放行是应用偏好，并会保存。它摆在当前对话旁边，却不是只影响这一条消息的设置。
- `index.html:242` 明确子代理开关只影响当前对话，运行中修改下一轮生效，已有子代理继续执行。它与全局权限、当前正在运行的数量是不同事实。
- `28-async-workspace.js:146` 起的“后台常驻”实际还能进入“停止后台任务并退出”，作用范围是整个应用。

推荐按下表归位：

| 当前元素 | 建议位置和形态 | 理由 |
| --- | --- | --- |
| 对话 / 概览、需求面板开关 | 项目内容区顶部；“概览”改为“管理” | 切换的是页面，不是输入方式 |
| 项目、分支 | 对照熟悉的参照布局保留上下文位置；去掉重复展示 | 防止发错对象，不为结构整齐而改变已有操作习惯 |
| 改动文件数、增删行数 | 保留熟悉的改动入口，完整文件列表进入差异面板 | 先减重复信息，不预先规定必须迁往页头 |
| 附件 | 输入框左下角保留 | 直接参与本条消息 |
| 模型、思考强度 | 保留输入附近熟悉的选择方式与相邻关系，不强制合成一个菜单 | 显示实际生效值，避免为少一个按钮增加修改步骤 |
| 结伴开发 / 自主推进 | 保留输入附近的模式快捷入口，详细配置按需展开 | 保持熟悉的模式切换，同时明确与自动继续的区别 |
| 鞭挞、轮数、阶段、停止原因 | 将这组特色功能的详细设置和计数按需展开；原有开关保持易达 | 优先收敛后加功能，不挤走通用控件；是否改名另看语义清晰度 |
| 自动放行 | 输入附近保留简短权限入口，详细规则进入权限设置 | 熟悉的快捷入口与应用级生效范围同时保留 |
| 子代理准入 | 对话运行设置；实际活动出现在运行详情 | “允许派发”与“当前运行几个”分开，下一轮生效仍需就地反馈 |
| 未派遣、0轮 | 默认不占位；在展开设置或确有异常时显示 | 空状态没有持续占据注意力的价值 |
| 旁路提问 | 运行时按需进入，先核对熟悉的提问与插话流程；“另问一个问题”仅为候选文案 | 让用户理解不会打断当前工作，不先造另一套发送习惯 |
| 后台常驻 | 应用级状态菜单；断线等异常时才提高显著性 | 常态不需要占据发送工具条 |
| 排队 / 插入 | 保持与发送动作相邻，按参照交互决定呈现方式，不强制发明分裂按钮 | 用户能判断消息何时送达，发送习惯保持一致 |
| 语音 | 保留熟悉的图标入口，启用后展开语音控制 | 不因表面减负而隐藏已习惯的常用入口 |
| 停止 | 保留在输入/发送附近，运行中直接可达 | 不迁往独立运行页；取消后续自动继续与停止所有后台另行区分 |

位置关系示意如下，最终控件排列按熟悉的参照界面核验，不把这张示意当成另起一套界面的定稿：

```text
项目名称 / 当前对话                             改动 6
对话  |  管理                                   工作清单

对话正文
当前执行：生成中  14:27

┌───────────────────────────────────────────────────┐
│ 输入消息……                                        │
│ ＋   模型 ▾   思考 ▾   模式/权限     …    停止  ↑  │
└───────────────────────────────────────────────────┘
```

示意图强调位置归属，不是新增所有常驻文字。空闲时没有运行行；输入为空时不强调发送；有草稿且任务在跑时，投递与停止仍可分别触达。模型信息与非默认的关键设置保留可见摘要，不能把所有东西一股脑塞进“更多”。

尤其要保留三项独立语义：**协作方式决定如何做，自动继续决定是否进入下一轮，权限决定哪些动作可执行。** 可以在同一设置面板分组呈现，不能合成一个意义不明的“自动模式”开关。现有结伴模式也能自动继续，简化界面时不能偷偷改变这个行为。

不以固定的 4–6 个入口作为硬目标。先保留熟悉的通用操作，再减少重复状态、空计数和特色功能的常驻细节；以中英文、缩放和实际运行状态验证密度，不继续缩小字号和点击区域，也不为了少一个按钮增加操作步骤。

**三、“概览”应改成项目管理，并按用户工作组织内容**

当前 `25-softwire-view.js:33–39`、`:119–138` 将需求、记忆、历史、工具、验证交付、子任务和运行用量作为七个并列模块，旁边还有完整工作列表、最近回复与待处理入口。`25-softwire.js:245` 起又负责需求详情、验证交付、工具和其他模块管理。这已经承担项目管理和运行检查的职责。

“概览”通常让人预期短摘要。用户进入后却能筛选、登记、进入模块、看证据、控制运行、向选中对象发消息，名称低估了页面实际职责。只换标题仍不够：现在七个模块按内部机制排列，用户必须自己从工具、历史和用量中拼出“当前做到了哪里”。

建议保留项目层级，项目内显示“对话 / 管理”；页面完整名称使用“项目管理”。全局继续叫“工作台”，避免两个层级都叫工作台或控制台。管理页的摘要部分可以叫“概况”，不再让整个管理系统都使用“概览”这个名称。

推荐呈现顺序：

1. **需要处理的事项**：只有实际存在才出现，写清影响哪个工作和可以做什么。
2. **工作清单和当前执行**：需求/缺陷是主体；运行状态附着明确的工作或对话，不能靠 `doing` 推断此刻在跑。
3. **最近交付**：能用什么、如何打开、验证到了哪一步。这比把最新三条模型回复直接搬过来更有价值。
4. **项目资源与运行详情**：记忆、文件、工具、历史、子代理、用量保留入口，使用时展开。已有独立的文件和记忆管理页继续承担完整管理，不再复制一套列表。

若暂无结构化交付数据，先显示“最近活动”及其事实来源，不把模型的一句“已完成”自动升级成交付。现有代码已有交付文件和批次证据入口，可优先复用。

七条波形可以保留为展开后的运行检查视图。默认页面把需求进展、可用成果和需人处理的事情放在前面；内存检索、工具调用、token 用量不需要始终和需求占相同的视觉权重。

管理页继续使用共享输入框，但输入上方必须标明实际接收者；明确切换模块才允许切换对象，后台事件不得改变发送目标。现有同一 composer、草稿隔离、发送目标快照值得保留，不要为了重排布局再创建第二份输入状态。

**四、需求栏红框里的对话内容应移除，关联能力保留**

这不是随机消息渲染到了错误位置，而是列表设计主动混入了运行中的对话：

1. `26-project-conversations.js:216` 复用 `renderWorkFocus()` 绘制右侧需求栏。
2. `25-softwire-view.js:349–356` 有线路时先绘制 `line.label`；没有条目就绘制“运行中，尚未关联需求”。
3. 同文件 `:407–408` 把尚未关联条目的运行线路追加到需求分组之后。
4. 当前对话未手动命名时会用实际用户输入作为标题。截图中的长指令正是这种标题，当前渲染又未在该行限制长度。

因此，**只把标题截成一行仍然保留了错误的对象归属**。需求栏应只列需求和缺陷。运行中未关联条目的对话放回对话导航或运行区域；若用户需要关联工作，再提供“关联工作”动作，不自动建立需求。

已经关联工作时，可以在工作详情显示“负责对话 →”或紧凑状态，例如“执行中 · 打开对话”，不把完整对话标题塞进需求行。删除这里的展示不影响对话记录、运行状态和原本的需求关联数据。

列表其余部分还可进一步减负：

- 现在每个条目有编号/状态/优先级、两行标题、类型/标签、批次格/数字等多层内容。窄栏只适合快速找条目，不适合展示完整管理信息。
- 建议窄栏保留“编号 + 短标题 + 状态”；优先级为次级信息，标签按筛选需要显示。批次先用“已完成 3/4 批次”，默认不再同时画一排粗进度方块。
- 批次是离散完成数，不是工作量百分比；不得把 3/4 写成“项目已完成 75%”。
- 进行中、待开始、待外部验收、已阻塞、已停车保留业务区分，但可先展示“进行中”和“待开始”；其余收在分组和筛选中，原因在详情可见。
- 底部“未完成/可执行/阻塞”矩阵更适合完整管理页。窄栏顶部可保留短计数，避免列表、对话、全量统计在一条狭窄列中同时争位置。
- 同时容纳需求和缺陷的区域应叫“工作清单”；“需求”留给其中的类型筛选。只改侧栏名字而不改完整列表页，会继续出现命名不一致。

**五、颜色问题来自当前规则本身，也来自缺少主次**

当前源码不是未按旧红绿规范实现。`brand_refresh.md:7` 已声明替代旧配色，`:35–47` 明确将失败与注意都放入橙色系；`ui_color_semantics.md:3` 也注明旧映射已转为历史记录。

源码实际色值：

| 用途 | 深色主题 | 浅色主题 |
| --- | --- | --- |
| 强调文字 | `#ffad66` | `#934100` |
| 失败 | `#ffad66` | `#963f00` |
| 注意 | `#ffc18b` | `#874500` |
| 主要操作 | `#ff8700` | `#c56500` |
| 完成 | `#39d8f6` | `#006579` |

见 `style.css:24–33`、`:152–156`。深色主题强调文字与失败完全同色；浅色下强调、失败和注意都是接近的棕橙色。虽然文字/字形可以区分，但快速扫视时用户仍需逐字读。截图中模式、运行、自动放行、后台常驻、停止和发送同时带橙色，进一步稀释了重点。

建议保留亮橙、墨蓝、电光青的品牌身份，重新分配功能色和视觉重量：

| 对象 | 推荐表达 |
| --- | --- |
| 品牌与主要操作 | 橙色；同一操作区只保留一个主要填充按钮 |
| 选中页签、普通配置、后台已连接 | 中性文字、底色或细线，避免全部染橙 |
| 正常运行 | 小状态点或短阶段标签；同一对话附近保留一处主运行状态 |
| 等用户、阻塞 | 有原因和动作的注意状态，不仅换色 |
| 失败 | 建议使用独立的错误色；例如明确的暗红，并保留文字/图标 |
| 完成 | 继续使用青色也可以；只标真实完成结果，不把开关“开启”画成成功 |
| 停止当前运行 | 次级控制；不要与主要发送操作争同等级填充，不把正常停止等同于失败 |

为失败引入独立功能色意味着调整品牌文档对提示色的三色限制，这是本次提出的设计改进，不是声称原实现违背了规范。若继续严格保留三色限制，至少把失败做成独立的图标、文字和容器形态，减少普通橙色状态；但快速区分仍会弱于独立错误色。
