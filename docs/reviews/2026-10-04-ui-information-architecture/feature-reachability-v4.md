## 为什么采用横向主干

调研了分层依赖图、严格树、主干加局部关系与依赖矩阵。当前有共享依赖，严格树要重复模块或丢关系；22 条正常依赖全部连线又不利于阅读。采用从左到右的依赖主干，省略可经其他节点到达的重复连接。当前约简后 8 条连接，全部是真实直接关系；可达性与原 22 条一致。

点击模块再进入“使用方 → 当前模块 → 直接依赖”，完整呈现其局部关系。开发依赖保留在来源清单。静态依赖与下方项目级运行数据分别说明，不把项目均时归因到某个模块。

参考：[Graphviz 分层布局](https://graphviz.org/docs/layouts/dot/)、[传递约简](https://graphviz.org/docs/cli/tred/)、[yEd 正交路由](https://yed.yworks.com/support/manual/layout/layout_hierarchic_incremental.html)、[D3 树布局](https://d3js.org/d3-hierarchy/tree)。采用哪种呈现是针对本项目的设计判断。

## 运行数据如何接回已有能力

| 指标 | 本版口径 | 正式接入依据 |
| --- | --- | --- |
| 平均运行时长 | 已完成且计时完整的运行；失败、停止和刷新中断不混入 | 对话运行开始/终止事件；按运行 ID 配对 |
| 工具调用与失败 | 按调用 ID 去重，真实失败与规则拒绝、用户停止分开 | `crates/kanzei-core/src/runner/metrics.rs` 的本轮 `RunMetrics` |
| 记忆召回与注入 | 按运行内独立记忆累计条次，全局/项目分开 | `crates/kanzei-core/src/store/telemetry.rs`；排除用户搜索 |
| 记忆读取 | 独立观察项，未观察和观察到空列表分开 | `crates/kanzei-core/src/store/memory_observations.rs` 的 `read_ids / read_observed` |

读取不是效果证明。正式服务的召回事件需要保留事件 ID 去重，不应只看全对话消息累计，也不能用注入次数代替读取。原型新演示轮次没有记忆观察，因此保留为空。

## 工作与窗口的行为

当前清单属于对话，完整项目台账仍可进入。闲置切换时旧工作回到待开始并保留进度；运行中选择仅记录下轮目标，这轮仍显示原需求编号。草稿、阻塞、待验收、已完成和存在契约缺项的工作不可执行；另一正在运行的对话占用的工作不可直接转交。下轮目标失效时保留待发送消息，等待调整或明确取消切换。

活动栏和网页浮窗按对话保存，互相独立开关。手动选择历史预览后，新调用只更新选择列表，不重建正在阅读的网页。刷新页面暂停未完成演示，保留记录；切换项目不会把别的对话输出弹到当前页面。

## 仍未补齐的正式流程

会话重命名/置顶/分叉/交接/导出，待回答与决定复核，需求依赖影响范围，子代理分支采纳与冲突，规范建议稿对照，记忆图谱与详细追溯，实际进程/网页连接与重连，手机/远端/语音/真实计划执行仍待接入。

这些能力已有明确归属，不需要再堆一级菜单。原型可以验证呈现和动作，正式后端连接另行落地；不能将“入口存在”写成“所有功能已可用”。
