
# Agent 开发规则(强调仅仅适用于代码开发，不适用于其他任务)

## 1. 语言与沟通

- 所有回复、解释、代码修改说明、提交说明、测试说明必须使用简体中文。
- 在需求边界不清楚时，必须先提问确认，不允许在关键问题上自行假设后直接实现。
- 若问题不影响数据模型、权限、安全、外部接口、核心业务流程，可做低风险合理假设，但必须在说明中明确假设内容。
- 每次回答和修改代码前，需要先充分理解当前项目结构、已有实现、调用链和上下文。
- 开发时应优先复用项目中已有的函数、接口、工具方法和设计模式，不要重复造轮子。
- 涉及数据模型、权限体系、审批流程、工作流执行语义、第三方集成、部署流程等高影响改动时，必须先给出方案并等待确认，再进入实现。

## 1.1 需求取活与阻塞调度

- 需求列表按文件顺序自上而下扫描，顺序代表用户意图；priority 只用于背景判断，不得改变取活顺序。
- **`阻塞:` 字段只留给外部阻塞**——即解除权不在 agent 手里的四类：①已经把方案发给用户、正在等回复；②缺凭据/权限/环境；③依赖外部服务或他人；④用户明确宣布该条自己直营。写入时必须带**具名的解除人**（谁做什么才能解除），写不出具名解除人的就不是外部阻塞。
- **下列一律不算阻塞，不得写入 `阻塞:` 字段**：涉及多文件／跨层／数据模型（这是工作量，不是阻塞）；"需先确认方案"但从未真的问过用户；上游条目自身只是被自记阻塞（伪传递阻塞）；本轮没想清楚怎么做。这些只写 `进展:`，不影响调度。
- 某条一时推不动就在 `进展:` 记一句原因直接跳到下一条，不得让它拖住后续队列；`进展:` 是面包屑，不压制取活。
- blocked 项不得被误标为 done；解除阻塞后再恢复推进。追踪工具没有 blocked 状态时保留原状态，调度器以 `阻塞:` 字段判断跳过。
- 触碰任一条目时顺手复核它的 `阻塞:` 是否仍成立：解除条件已满足、依赖已归档、方案早已确认的，**当场清空该字段**。阻塞只进不出会在若干轮后锁死整个队列。
- WIP 同时最多 2 个 doing；blocked 的 doing 项不占用可执行槽，但仍计入 doing 总数。启动后续需求前必须确认 doing 总数未超过 2，并且新项确实可做。
- 已完成的 doing 需求必须立即用 `req update <id> done` 关闭。
- **全部条目都 blocked 是队列异常，不是可接受的终态**（list 会给出 `[调度死锁]` 横幅）。此时必须：先逐条复核并清掉不成立的阻塞；复核后仍全阻塞，才回复用户并**逐条点名缺的是哪一个具体决策**。禁止以"没有可执行条目""本轮停止"之类的纯文本收尾。

## 1.2 关闭边界:可用即关闭(2026-08-07 用户定调)

- 缺陷/需求以「功能可用」为关闭界:核心行为已实现、有可运行的自动化验证(单测或集成任一)即关闭;不因缺 E2 夹具、UI harness、并发压测等验证增强项长期滞留 fixing/doing。
- 残余验证与质量缺口不丢弃:关闭时转移到专门条目(如 R-101 E2 清单)或新开需求/缺陷,并在关闭条目进展里注明去处。
- 不允许关闭的情形:验收的功能性条款未实现、存在已知数据丢失或安全风险、或没有任何自动化验证。
- 判定口径:问「现在用它会不会坏」,而不是「测试矩阵是否完备」。

## 1.35 标签与依赖字段(2026-08-08 用户定调)

- 标签受控词表(单选,不再用自由英文标签与 类型/领域 字段):前端 | 后端 | 核心 | 模型 | 发布 | 流程。
  前端=ui 界面与交互;后端=Tauri 命令/会话/存储/tracker 服务;核心=runner/harness/tools/memory/CLI 引擎;模型=provider 协议/凭证/限流;发布=构建/安装/更新;流程=规范/度量/验收/测试基建。
- `依赖:` 只列**仍未完成**的阻塞项;依赖关闭后在下次触碰该条目时把它移入 refs——已满足依赖滞留在依赖字段会让取活调度误判阻塞(2026-08-08 实测 R-083 因 9 个已归档依赖被卡)。

## 1.3 工作粒度与验证选择(2026-08-07 用户定调)

- 单轮粒度 = 一个完整条目:以做完当前这一条缺陷/需求为目标;同构批量改动(i18n、重命名、格式迁移)一轮吃掉完整类别,禁止两三处一轮的微切片;确实超出单轮容量才按验收子项分轮,并在进展里写明批次边界。
- 验证与改动面匹配:纯 ui/(html/js/css)改动跑 node --check 与冒烟脚本即可;动了 crates/ 才跑 cargo test(先定向,提交前全量一次);与改动无关的套件不跑——无信息量的测试本身就是浪费。
- **前端改动不得只以 `node --check` 作为验证证据**:它只查语法,查不出 ReferenceError、初始化崩坏和渲染错位(D-048 就是带着 [done] 出货的)。必须同时跑 `node scripts/ui-runtime-smoke.mjs`,且新增的交互要在冒烟里留下对应断言——修了什么就断言什么,否则同类回归下次照样溜过去。
## 2. 代码修改原则

- 不要引入不必要的框架、抽象层、兜底逻辑或兼容逻辑。
- 不要为了“看起来完整”而实现简化版、替代版或占坑版功能。
- 如果某部分暂时无法完整实现，可以明确留下 `TODO`，但不能用低质量简化实现代替正式实现。
- 任何有风险的实现，必须先说明风险点，再进行修改。
- 不允许在需求不清楚、数据结构不确定、接口行为不明确的情况下自行扩展实现。
- 修改应保持小步、可验证、可回滚，避免把无关重构和业务改动混在一起。
- 不要改动与当前任务无关的文件，不要混入无关格式化。

## 3. 命名与代码风格

- 项目内部统一使用 `snake_case`。
- 字段名、变量名、函数参数、请求参数、返回数据结构在业务代码中都应统一为 `snake_case`。
- 如果第三方接口返回 `camelCase`，必须在调用层或适配层统一转换为 `snake_case`。
- 业务代码中不应额外兼容或兜底读取 `camelCase` 字段。
- 禁止在同一模块或同一数据流中混用 `snake_case` 和 `camelCase`。
- 前端如果受框架限制必须使用组件事件或库约定命名，应限制在 UI 层，不得污染后端 API 契约和业务数据结构。

## 4. 架构与契约规则(kanzei 版)

- `kanzei-llm` 的 `LlmEvent` / `Part` / `LlmRequest` 变更，必须同步全部三个协议实现（anthropic / openai / openai_responses）和 runner，不允许只改一处。
- `kanzei-harness` 的 `Tool` / `ToolOutput` / 权限契约变更，必须同步 kanzei-tools 所有工具、runner、kz CLI 与桌面端事件转发。
- 桌面端新增/修改 Tauri command：必须注册进 `invoke_handler`，入参返回结构变更必须同步 `ui/main.js` 调用方；新增前端事件必须经 `on()` 订阅（listen 失败要可见）。
- `kanzei.toml` 配置 schema 变更必须向后兼容（serde default），设置页表单必须透传新字段，禁止保存时丢字段。
- 权限规则是硬门禁：任何"规则"能用代码强制的绝不只写进提示词。
- M2 起 SQLite 表结构变更需附迁移与回滚说明。

## 5. 终端与命令规则

- 默认终端环境是 PowerShell。
- 除非明确是在外部 Linux 服务器上执行，否则不要使用 Linux 风格命令。
- 本地命令应优先使用 PowerShell 兼容写法，避免使用会在 PowerShell 中报错的命令。
- 如果要进行长时间训练、部署、批量迁移、长时间构建等流程，先给出指令让我来执行。
- 执行命令前应确认当前目录。
- 运行测试、构建、格式化前，应说明将验证什么。
- 不要执行破坏性命令，除非我明确要求并确认风险。

## 6. 分支与提交流程(kanzei 版)

- 默认且唯一开发分支是 `main`，直接在 `main` 上提交，无 merge/部署环节。
- 开发前 `git status` 检查工作树，提交前确认只包含本次任务的必要改动。
- `.kanzei/project/` 下的需求、缺陷、规范文档是项目资产，随代码一起提交；`.kanzei/summaries/` 对话总结与临时文件不提交。
- commit message 使用中文或英文均可，但一律**不带任何 Co-Authored-By 署名**。
- push 前设置代理：`$env:HTTPS_PROXY = "http://127.0.0.1:12000"`。

## 7. 测试与验收

- 代码修改完成后，必须提供测试用例。
- 测试说明需要包括：
  - 测试什么功能；
  - 如何触发测试；
  - 预期结果是什么；
  - 什么情况下算测试完成。
- 修改后应优先运行与改动相关的最小测试集。
- 对于核心流程、权限、审批、工作流、数据库迁移、前后端契约变更，需要补充重点回归测试范围。
- 前端改动至少需要说明：
  - 影响页面；
  - 用户操作路径；
  - 预期 UI 状态；
  - 失败或空状态表现。
- 后端改动至少需要说明：
  - 影响接口；
  - 请求和响应字段；
  - 权限要求；
  - 错误码或异常行为。
- 部署完成后，需要根据测试用例验证功能是否正确。

## 8. 文档与计划维护

- 每次完成大规模改动后，需要及时更新相关的 plan、设计说明或项目文档。
  -必须维护的文档有需求文档和缺陷文档，维护归档的和现在进行的每次长上下文修复后记得更新，并且在最近的一次对话引用。
- 小修 bug 不强制更新设计文档，但最终说明中必须写清影响范围。
- 文档更新应反映真实实现，不要写尚未完成的功能为已完成。
- 如果存在未完成事项，应明确标记为 `TODO` 或后续计划。
- 文档中的产品状态、技术状态和 TODO 必须保持一致，避免同一能力同时被描述为”已完成”和”未完成”。

## 9. kanzei 本仓库:构建与发版(优先级高于上文通用规则)

- 本仓库是 Rust workspace:`crates/kanzei-{harness,llm,core,tools,app}` + `crates/kanzei`(bin `kz`)。
- **分支流程**:日常开发(含 agent 自举)一律提交到 `dev` 分支;`main` 只接收来自 dev 的合并,保持随时可发布。**main 常驻发布树**(`C:\Users\kanzei\Documents\kanzei-release`),主工作树里 `git checkout main` 会因分支被占而失败——合并发布一律在发布树执行:`git -C <发布树> fetch origin && git -C <发布树> merge origin/dev --ff-only && git -C <发布树> push`,再跑发布树里的 `package.ps1 -Publish`。禁止直接在 main 上做开发提交。
- **提交身份铁律**:commit 的 author/committer 必须且只能是 kanzei 本人(`kanzei <vraniumzwt@gmail.com>`);message 不得包含任何 `Co-Authored-By` 尾注(GitHub 会把共同作者计入贡献者头像墙)。任何工具/AI 不得以自己的身份出现在 git 历史里,发现异常身份立即改写修正并强推。
- 测试:`cargo test --workspace`,全绿才算改动完成;单 crate 快速检查用 `cargo build -p <crate>`。
- **发版安装(用户可见的”构建”)**:`.\scripts\release.ps1`
  - 流程 = 全量测试 → 安装 `kz` 到 `~\.cargo\bin` → release 构建桌面端 kzapp 并复制安装;
  - **桌面端只有一个安装位:`%LOCALAPPDATA%\kanzei\kzapp.exe`**(应用内更新与开始菜单都指向它)。`~\.cargo\bin` 只放 `kz` CLI 与转发启动器 `kzapp.cmd`,**绝不能再放 kzapp.exe**——两份副本各自更新就会出现"发布了但仍在跑旧版"(D-145)。判断当前跑的是哪份:`Get-Process kzapp | Select-Object Path`。
  - kzapp 正在运行时复制会失败,脚本会把新版本存为 `kzapp.exe.pending` 并提示——此时告知用户”关闭 kzapp 后重跑 release.ps1”,**不要强杀用户正在使用的窗口**;
  - `-SkipTests` 仅在用户明确要求时使用。
- 版本验证:`kz --version` 输出 `kanzei 0.1.0 (<git hash> <日期>)`;桌面端右下角有相同版本徽章,以此确认用户装到的是新版。
- 网络:`git push` / 访问 GitHub 需要代理,PowerShell 里先 `$env:HTTPS_PROXY = “http://127.0.0.1:12000”` 再执行。
- 提交规范:commit message 一律**不带任何 Co-Authored-By 署名**;提交前 `git status` 确认只包含本次任务的必要改动。
### 9.1 发布部署(两条通道)

- **开发通道(自举机)**:`.\scripts\release.ps1` = 全量测试 → 装 `kz` → 构建并安装 kzapp;kzapp 运行中会落 `kzapp.exe.pending`,**下次启动自动接力替换**,无需手动处理。
- **发行通道(安装包)**:`.\scripts\package.ps1 -Publish` = `cargo tauri build` 产出 NSIS 安装器 `dist\kanzei-setup-<hash>.exe` → `gh release create build-<hash>` 发布到 GitHub Releases。
  - 应用内更新以**最新 release** 为源:启动 3 秒后静默检查(有新版弹 toast),设置页「检查更新」可手动查 + 一键下载安装;
  - 所以:想让安装版用户收到更新,**必须带 `-Publish`**;只跑 release.ps1 安装版是感知不到的。
- **发布时机与检查单**:完成一批已验证需求/缺陷后发布;发布前必须 ①`cargo test --workspace` 全绿 ②工作区干净且已 push ③`kz --version` 的 hash 与 HEAD 一致。
- **发布树(worktree)**:发布统一从 `C:\Users\kanzei\Documents\kanzei-release`(`git worktree`,跟踪 main)执行:`git -C <发布树> pull` 后跑其中的 `package.ps1 -Publish`——与 dev 工作树完全隔离,发布时不需要 stash/打断正在进行的开发。**提交了不等于发布了**:安装版用户只认 Releases,合并 main 后记得发布。
- **Release 标签规范**:tag = `build-<short-hash>`,标题 `kanzei <日期> (<hash>)`;历史 release 不删除(更新只看 latest)。
- **产物卫生**:`dist/` 只保留最新安装器,`dist/`、`target/`、安装器一律不入库。
